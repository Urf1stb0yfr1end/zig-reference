# RFC process

Use an RFC for foundational abstractions, schema or canonical-source changes, naming/ownership policy, repository-wide API migrations, maturity policy, breaking build-system changes, and major Hyper-Zig architecture. Ordinary bug fixes, documentation corrections, and modules following accepted standards do not require one.

Copy `TEMPLATE.md`, choose the next unused number, mark it Proposed, and seek maintainer discussion. Accepted RFCs record resolution and lead to ADRs where a permanent rule is established. Rejected or withdrawn RFCs remain as architectural memory. Implementation cannot silently broaden an accepted RFC.
