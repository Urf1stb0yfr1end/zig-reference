MISSION

Build the next coherent Snowball Batch: the reusable RISC-V page-table foundation needed for future Hyper-Zig, RISC-V kernels, bootloaders, supervisors, guest-memory systems, and the Alpine riscv64 boot roadmap.

Do not build the whole hypervisor.

Do not attempt to boot Alpine in this task.

Build the smallest correct set of foundational modules that later host and guest translation layers can depend on.

The objective is to make future page-table, guest-memory, loader, trap, and virtual-device work dramatically easier and safer.

CORE PRINCIPLE

Do not create one giant page-table module.

Separate architectural representation, indexing, walking, mutation, allocation ownership, and invalidation into precise reusable layers.

TARGET BATCH

Implement a coherent page-table foundation of approximately 5 to 8 modules.

The preferred architecture is:

1. riscv-sv39-page-table-entry
2. riscv-sv39-virtual-address-indexing

4. riscv-sv39-page-table-walker
5. riscv-sv39-page-table-builder

Do not add extra modules merely to increase the count.

If a proposed module is too small to justify its own contract, incorporate it into the most coherent neighboring module.

MODULE 1: RISCV SV39 PAGE-TABLE ENTRY

Create a typed, explicit representation of a 64-bit RISC-V Sv39 page-table entry.

It must cover:

valid bit
read bit
write bit
execute bit
user bit
global bit
accessed bit
dirty bit
physical page number fields
reserved-bit validation
leaf versus branch classification
legal and illegal permission combinations
conversion from page-frame address to PTE fields
conversion from PTE fields back to physical page-frame address
clear invalid entry construction
exact raw-value encoding and decoding
no silent truncation
no acceptance of reserved or malformed combinations

Important architectural rules must be encoded and tested, including:

write without read is invalid
branch entries must not contain leaf permissions
leaf entries must contain at least one of read or execute
misaligned superpage leaf encodings must be detectable
reserved bits must be rejected
physical page numbers must fit the supported architectural width
invalid entries must not accidentally expose stale address bits as valid mappings

The contract must clearly distinguish:

architecturally invalid encoding
valid branch entry
valid 4 KiB leaf
valid 2 MiB leaf
valid 1 GiB leaf

MODULE 2: RISCV SV39 VIRTUAL-ADDRESS INDEXING

Create checked decomposition and reconstruction for Sv39 virtual addresses.

It must provide:

VPN2 index
VPN1 index
VPN0 index
page offset
canonical-address validation
sign-extension validation
checked construction from indices and offset
page-size-aware alignment checks
leaf-level identification
range-boundary handling
no truncation of noncanonical values

Test:

lowest canonical address
highest positive canonical address
lowest negative canonical address
highest canonical address
noncanonical holes
all index boundaries
all supported leaf levels
misaligned addresses
round trips

Reuse distinct-memory-address-types and existing checked arithmetic where contracts fit.

MODULE 3: RISC-V PAGE-TABLE PAGE OWNER

Create an explicit owner for one page-table page or a bounded set of page-table pages.

The module must make allocation and cleanup responsibilities obvious.

It must define:

who allocates a page-table page
who owns it
how it is initialized to zero
how its physical frame identity is retained
how the host obtains a temporary mutable view when needed
how cleanup occurs
what happens after failed partial construction
what remains valid after move or transfer
whether copying is prohibited by contract
how pages are released to the physical-page-frame-allocator
how allocation failure is reported

Do not hide allocation.

Do not silently allocate through a global allocator.

Reuse:

physical-page-frame-allocator
physical-page-frame-number-and-address-conversion
fixed-bump-allocator where appropriate
fixed-free-list or fixed-capacity-object-pool only if their contracts genuinely fit

If the repository lacks a safe abstraction for obtaining a mutable memory view from a physical page frame, define the dependency boundary explicitly instead of inventing unsafe global behavior.

A callback or injected page-access provider may be appropriate.

MODULE 4: RISCV SV39 PAGE-TABLE WALKER

Create a read-only walker that resolves a virtual address through a supplied root table and page-access provider.

It must:

walk level 2, level 1, and level 0
identify branch versus leaf entries
return resolved physical address
return leaf level and effective page size
return mapping permissions
detect invalid entries
detect malformed branch entries
detect misaligned superpage leaves
detect provider failures
avoid allocation
avoid mutation
avoid undefined pointer assumptions
return structured failure causes

The walker must be independently usable by:

debuggers
mapping verification
guest-memory diagnostics
page-fault analysis
page-table builders
future Sv39x4 code where compatible

MODULE 5: RISCV SV39 PAGE-TABLE BUILDER

Create a deterministic builder for mapping and unmapping Sv39 ranges.

It must support:

map one page
map aligned ranges
unmap one page
unmap aligned ranges
query existing mappings
change permissions where safe
allocate intermediate table pages through injected ownership and allocation interfaces
reuse existing branch tables
reject conflicting mappings
reject overlap unless an explicit replacement operation exists
support 4 KiB leaves
support 2 MiB leaves
support 1 GiB leaves
select leaf sizes only when alignment and range permit
optionally expose an exact-page-size mode
rollback after partial failure
avoid leaking intermediate page-table pages
avoid corrupting existing mappings when a later allocation fails
deterministic traversal and mutation
structured errors
explicit invalidation requirements in results

Do not silently replace existing mappings.

Do not silently split a superpage unless the API explicitly performs and documents that operation.

Do not silently merge mappings.

Do not assume identity mapping.

Do not use global mutable state.

The builder should return a mutation result that tells the caller whether an SFENCE.VMA operation is required and what scope is sufficient.

MODULE 6: RISC-V SFENCE.VMA INVALIDATION

Create a narrow architectural invalidation interface.

It must represent and document:

global invalidation
address-specific invalidation
address-space-specific invalidation where ASID support is represented
address-plus-ASID invalidation
compiler ordering requirements
CPU ordering assumptions
unsafe boundary for actual assembly execution
testable command planning separate from privileged instruction execution

Tests must verify command selection and operands without requiring privileged execution.

The actual instruction wrapper may require an explicit unsafe or architecture-specific boundary.

Do not pretend hosted unit tests execute privileged invalidation.

Do not rely on memory or secondary summaries for bit positions, canonical address rules, superpage alignment, reserved bits, or SFENCE.VMA semantics.

Do not copy long passages from the specification.
