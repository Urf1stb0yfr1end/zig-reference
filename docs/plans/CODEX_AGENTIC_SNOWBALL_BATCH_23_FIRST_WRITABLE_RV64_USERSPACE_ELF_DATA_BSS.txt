GOAL

Prove the next smallest process-image fact:

A separately built real RV64 ET_EXEC userspace ELF containing a deliberately bounded writable PT_LOAD with initialized data and a non-empty BSS tail can be planned by the existing bounded-elf64-load-plan, loaded into allocator-owned user memory, initialized exactly from ELF file bytes, zero-filled exactly according to the planner, mapped with the exact planned non-executable writable permissions, observed and mutated by real U-mode code, and returned through the already-proven trusted supervisor boundary under strict real-QEMU evidence.

The central new truth for Batch 23 must be:

- planner-selected initialized writable bytes are copied exactly;
- planner-declared BSS bytes are zero before U-mode observes them;
- the writable segment is represented by an exact U RW/NX mapping rather than permission widening;
- real U-mode code reads the initialized data, observes zeroed BSS, writes a bounded value into that writable segment, then ECALLs back;
- supervisor evidence proves the expected post-U-mode mutation occurred in the same mapped physical storage;
- the existing executable ELF proof remains intact.

SCOPE BOUNDARY

Prefer the smallest architecture that proves the fact.

A suitable target is one tiny separately built RV64 fixture with exactly:

- one R-X PT_LOAD containing code;
- one RW- PT_LOAD containing initialized data plus a non-zero p_memsz - p_filesz BSS tail;
- one entry point inside the executable segment;
- no PT_INTERP;
- no dynamic linking;
- no relocations;
- no TLS;
- no shared-library semantics;
- no stack-construction ABI;
- no libc;
- no syscalls beyond the already-proven deliberate ECALL boundary.

If the existing Batch 22A planner currently admits this shape without semantic change, consume it unchanged.

If a genuinely reusable lower-level capability is missing, stop and classify it using the Agent Fast Path before adding project-specific code. Add a new reusable module only if the missing capability is truly general and not simply Batch 23 orchestration.

Use the existing repository primitives and Batch 22B machine composition as authoritative inputs. In particular:

- bounded-elf64-load-plan is the sole ELF acceptance/planning authority;
- existing allocator-owned physical memory machinery remains authoritative;
- existing Sv39 page-table entry/builder/walker machinery remains authoritative;
- existing typed memory address primitives remain authoritative;

- Batch 22B executable-segment proof must remain preserved rather than rewritten.

Do not duplicate ELF parsing or silently derive a second loader policy in recipe code.

MACHINE IMAGE REQUIREMENT

The new fixture must make the writable-segment facts independently inspectable.

The verifier must independently parse or inspect the emitted ELF strongly enough to establish at least:

- exact artifact identity used by the kernel build;
- PT_LOAD count and ordering;
- executable segment source/memory ranges and R-X permissions;
- writable segment source/memory ranges and RW- permissions;
- writable p_filesz;
- writable p_memsz;
- exact non-zero BSS length = p_memsz - p_filesz;
- e_entry and its relationship to the executable segment.

Do not trust only kernel-emitted claims for ELF structure.

LOAD REQUIREMENT

The kernel-side orchestration must consume the LoadPlan and perform only the machine operations implied by that plan.

For the executable segment, preserve the exact Batch 22B source-byte-to-loaded-byte proof and FENCE.I behavior.

For the writable segment:

1. allocate or reuse bounded allocator-owned physical storage that is explicitly accounted for;
2. establish an exact U RW/NX mapping for the planned virtual range;
3. copy exactly the planner-selected initialized file bytes into the intended destination;
4. directly compare every copied initialized source byte against the volatile loaded destination byte;
5. zero exactly the planner-declared BSS tail;
6. directly verify every BSS destination byte is zero before U-mode entry;
7. do not execute FENCE.I merely for writable non-executable data unless an existing contract requires it for a truthful reason;
8. perform SFENCE.VMA only if page-table translation state actually changed and report that truth precisely.

Do not collapse p_memsz to p_filesz.
Do not treat a digest as an exact-copy proof.
Do not widen writable data to executable.
Do not widen permissions to make the fixture convenient.

U-MODE BEHAVIOR REQUIREMENT

The guest program must make the new proof observable through real execution.

It should, using deliberately simple fixed operations:

- load a known initialized value from the writable PT_LOAD;
- confirm the expected initialized value;
- load one or more bytes/words from the BSS tail and confirm they are zero;
- write a distinctive bounded marker into the writable segment or BSS;
- place unique Batch 23 register markers into a small fixed set of registers;
- issue the deliberate ECALL;
- rely on the existing trusted supervisor trap path.

Avoid introducing a general userspace runtime or ABI. The fixture exists only to prove process-image writable-data/BSS behavior.

SUPERVISOR RETURN PROOF

After the ECALL returns to supervisor code, prove at least:

- cause is the expected U-mode ECALL;
- trap PC belongs to the independently reconstructed executable segment;
- expected register markers survived in the trusted trap frame;
- initialized data had the expected value before guest mutation;
- BSS was zero before guest mutation;
- the guest's expected bounded write is visible in the mapped writable physical storage afterward;
- executable segment bytes remain unchanged;
- writable PTE is U RW/NX;
- executable PTE is U R-X and not writable;
- W+X leaf count remains zero;
- SATP/root truth remains coherent;
- allocator/page-table accounting matches the deliberately introduced resources;
- no unrelated translation or permission drift occurred;
- supervisor continuation is reached.

PROOF QUALITY

Do not call digest equality exact byte equality.

Where exact bytes matter, compare bytes directly.

Where zero-fill matters, inspect the destination bytes directly before guest execution.

Where post-execution mutation matters, inspect the actual mapped destination storage after return.

Where permissions matter, derive them from actual page-table leaves rather than a textual claim.

Where ELF structure matters, derive it independently from the exact emitted artifact.
