1. WHERE BATCH 26 STARTED
======================================================================

Batch 25B was already a real machine milestone, not a hosted simulation. It proved the Linux/RV64 syscall boundary over the Morphic semantic seam and the generation-bearing resource world. The inherited machine path had:

- real RV64 U-mode ELF execution;
- S→U→S ECALL/trap transitions;
- exact returning sepc+4 behavior;
- terminal exit/exit_group behavior;
- active Sv39 translation;
- W+X=0;
- Linux fd 0/1/2 bindings;
- dup/close alias lifetime;
- EBADF/EFAULT/ENOSYS behavior;
- project 57 generation-bearing ResourceRef identity;
- stale-generation rejection;
- deterministic stdin with the resource slot deliberately reused at generation 2;
- two independent QEMU machine runs;
- strict mutation rejection;
- Morphic equality evidence.

Batch 26 was intended to cross the next ecosystem threshold in one campaign:

    Batch 25B resource/fd world
          ↓
    file + directory/path world
          ↓
    mmap/protection/unmap world
          ↓
    exec image replacement
          ↓
    PT_INTERP / dynamic-ELF handoff
          ↓
    enough process-image reality to pressure musl/BusyBox/Alpine next

The intention was never to implement a complete POSIX kernel. The intention was to create the minimum permanent mechanisms needed to inherit the next large software surface.

2. WHAT THE FIRST BATCH 26 RUN ACTUALLY BUILT
======================================================================

The run did not finish the final real-machine integration. It did, however, build two new reusable substrate modules and extend the ELF planning boundary.

---------------------------------------------------------------------
2A. PROJECT 58 — BOUNDED FILESYSTEM
---------------------------------------------------------------------

Project 58 created a Linux-independent bounded filesystem object world with:

- a mandatory root object;
- directory objects;
- file objects;
- ObjectId identity;
- bounded inline names;
- bounded inline file content;
- absolute-root traversal;
- traversal relative to an explicit starting directory ObjectId;
- deterministic lookup;
- bounded offset reads;
- validation-before-mutation behavior for failed creation/lookup paths.

The important identity separation is intentional:

    filesystem ObjectId
          ≠
    Morphic/project57 ResourceRef
          ≠
    Linux process-local fd integer

Project 58 does not own Linux syscall numbers, Linux errno, Linux fd allocation, AT_FDCWD, Linux open flags, or register ABI identity. Those remain compatibility-edge responsibilities.

This means the filesystem substrate can later be reused by QuirkM, WASI/resource adapters, Linux compatibility, or other personalities without importing Linux descriptor semantics into the permanent mechanism.

---------------------------------------------------------------------
2B. PROJECT 59 — BOUNDED ADDRESS SPACE / EXEC IMAGE CANDIDATE
---------------------------------------------------------------------

Project 59 created reusable candidate/policy state for:

- page-aligned mappings;
- non-overlap validation;
- map;
- protect;
- unmap;
- access queries;
- deterministic fixed capacity;
- validation-before-mutation;
- unconditional W+X rejection;
- staged executable-image candidate planning;
- main-image entry tracking;
- optional interpreter-image tracking;
- copied interpreter pathname;
- distinct main entry and eventual interpreter entry.

Project 59 is deliberately NOT the physical page allocator and NOT the Sv39 page-table implementation.

The intended composition is:

    project 59 validated mapping/image candidate
          ↓
    existing physical ownership + project 49 Sv39 mapping/protection/unmap
          ↓
    project 48 invalidation where required
          ↓
    real machine state

This preserves one source of truth for actual page-table mutation instead of creating a second virtual-memory implementation inside the candidate module.

---------------------------------------------------------------------
2C. PROJECT 54 — DYNAMIC ELF / PT_INTERP PRESSURE
---------------------------------------------------------------------

Project 54 originally had an intentionally narrow static planner:

    plan(...)
      -> RV64
      -> little-endian
      -> ET_EXEC
      -> validated PT_LOAD segments
      -> static executable acceptance surface

That narrowness was a feature because earlier machine proofs depended on a strict static contract.

The first Batch 26 design attempted to compose that static-only planner into the new dynamic ELF/PT_INTERP path. This was the first serious architecture defect found during review: the static planner intentionally rejected ET_DYN, PT_INTERP, PT_DYNAMIC, TLS, shared-library features, etc., so treating it as the dynamic handoff planner was contradictory.

The repair did NOT weaken the static proof.

Instead Project 54 gained a second adjacent surface:

    plan(...)
        strict static ET_EXEC contract
        previous proof preserved

    planDynamic(...)
        RV64 ET_EXEC or ET_DYN
        validated PT_LOAD segments
        a bounded owned PT_INTERP pathname
        PT_DYNAMIC represented as userspace-loader responsibility
        no kernel relocation

DynamicLoadPlan owns the interpreter pathname and the validated load plan, but it deliberately does not become a dynamic linker.

The permanent rule is:

    kernel maps and hands off
    userspace loader relocates

Do not move ELF relocation into the kernel merely to make the proof easier.

======================================================================
3. THE TWO REVIEW BLOCKERS THAT PREVENTED THE FIRST MERGE
======================================================================

PR #52 contained the new substrates but was NOT immediately mergeable after review.

Two blockers were identified.

---------------------------------------------------------------------
3A. BLOCKER: STATIC-ONLY PROJECT 54 USED FOR DYNAMIC HANDOFF
---------------------------------------------------------------------

Project 59's original dynamic/interpreter design composed Project 54 while Project 54's only accepted planner was the narrow static ET_EXEC planner.

That meant the architecture claimed representability for a dynamic/PT_INTERP handoff through a component whose contract explicitly rejected the required ELF forms.

This was repaired by preserving static plan(...) and adding the distinct planDynamic(...) / DynamicLoadPlan boundary described above.

---------------------------------------------------------------------
3B. BLOCKER: INVALID FILESYSTEM CAPACITY
---------------------------------------------------------------------

Project 58 initialized:

    count = 1

because the root object always exists, but its generic constructor originally permitted:

    FileSystem(0, ...)

That allowed a type whose object array had zero slots while its logical state claimed one root object, making root initialization/indexing structurally invalid.

The repaired FileSystem type now rejects at compile time:

    object_capacity == 0

and also rejects capacities larger than the complete u16 ObjectId namespace.

Because ObjectId is enum(u16), the valid maximum object capacity is 65,536 slots (indices 0..65,535).

Dedicated compile-fail fixtures require both invalid forms to be rejected with the intended diagnostic.

This was a workflow/continuation-state problem, not evidence of corrupted source code.

The important lesson for future runs is:

- start Codex from current main;
- let its task own its generated work branch while the task is active;
- do not manually patch that same task branch mid-run unless we intentionally abandon the Codex continuation relationship;
- when external repair is necessary, preserve a branch/checkpoint first and treat the new state explicitly as the next authoritative baseline.

15. MINMAX ROADMAP — FEWEST LARGE INHERITANCE GATES
======================================================================

The old numbered roadmap remains useful as an internal checklist, but it must not force one campaign per number.

The preferred strategic compression from current main is approximately FIVE large inheritance campaigns.

The question at every boundary is:

    What is the smallest missing permanent surface whose implementation causes the largest existing software world to become ours?

Leverage metric:

                    useful existing software newly reachable
    LEVERAGE   =   ------------------------------------------
                         permanent new kernel complexity

---------------------------------------------------------------------

---------------------------------------------------------------------

Pressure target:
real RV64 userspace file + mapping + exec + PT_INTERP path

Required proof:

    program A
      -> openat deterministic file
      -> read through real resource binding
      -> mmap real userspace memory
      -> mprotect real mapping
      -> prove changed access/fault semantics

    python3 tools/verify-freestanding-riscv64-file-memory-exec.py

---------------------------------------------------------------------
CAMPAIGN 2 — MUSL + BUSYBOX PRESSURE, NOT A SYSCALL CHECKLIST
---------------------------------------------------------------------

Do not create separate external batches merely named threads, signals, futex, poll, pipe, tty, time, etc. Use dynamic musl + BusyBox as the pressure oracle and implement the smallest coherent set it actually requires.

Likely pressure may include:

- process/thread creation;
- TLS;
- futex;
- signal handling/masks/return;
- pipes;
- poll/ppoll and perhaps epoll only if actual pressure requires it;
- clocks/timers/sleep;
- brk/mmap refinements;
- seek/stat metadata minimums;
- tty/ioctl minimums;
- sockets/DNS only when selected BusyBox/musl pressure reaches them.

Likely does not mean pre-implement everything. Instrument actual musl/BusyBox failures and repair the first missing permanent mechanism.

Acceptance target:

    dynamic musl works
        ↓
    BusyBox runs
        ↓
    BusyBox /bin/sh works
        ↓
    representative real shell commands work

One mechanism that unlocks multiple later surfaces counts as one permanent mechanism, not multiple batches.

---------------------------------------------------------------------
CAMPAIGN 3 — ALPINE + APK INHERITANCE GATE
---------------------------------------------------------------------

Once dynamic musl/BusyBox is viable, use a minimal Alpine userspace as the next oracle.

Do not manually build Python/Node/Clang/Wasmtime support as separate kernel projects first.

Target:

    Alpine userspace
        ↓
    /bin/sh
        ↓
    required filesystem/process/network minimums
        ↓
    apk works
        ↓
    package ecosystem becomes reachable

The pivotal gate is not merely printing an Alpine banner. It is package-manager capability:

    download/configure/install/run

Once apk works, pressure can come from existing packages rather than imagined ABI completeness.

Inheritance examples after that gate may include Python, Node, Clang, Wasmtime and many other packages, subject to whatever packages and dependencies are actually available in the selected Alpine repository.

This is the core MinMax multiplication step:

    relatively small compatible kernel surface
          ↓
    apk
          ↓
    enormous existing software surface

Likely pressure may include:

- shared mappings;
- mature threads/TLS/futex;
- signals;
- poll/epoll;
- pipes/event-style descriptors;
- clocks/timers;

Again, likely does not mean implement all of these in advance.

Acceptance target:

        ↓

This yields a huge inheritance jump before native hardware virtualization exists.

17. MINMAX DECISION LAW FOR FUTURE CODEX RUNS
======================================================================

Before implementing a new permanent mechanism, ask in order:

1. What real inheritance target is currently failing?
2. What is the first missing semantic/mechanism fact that prevents that target from continuing?
3. Does an existing module already solve most of it?
4. Can the missing behavior be implemented once below multiple compatibility personalities?
5. What Linux-specific quirks can remain quarantined in the Linux adapter?
6. Can the same mechanism later serve QuirkM and/or WASI without inheriting Linux identity?
7. Is there a smaller mechanism that unlocks the same target?
8. Can an existing software ecosystem perform the rest of the work for us once this one gate exists?
9. What decisive real-machine or real-software proof establishes that the inheritance boundary was actually crossed?

Never substitute:

    "Linux has syscall X, therefore implement X"

for:

    "our current inheritance target failed because semantic capability Y is missing; implement the smallest reusable Y."
