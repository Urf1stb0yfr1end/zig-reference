CODEX AGENTIC SNOWBALL BATCH 11 — FREESTANDING RISC-V EXECUTION BOUNDARY

MISSION

Remove Linux userspace from beneath the already-proven Morphic execution path without rewriting settled Morphic semantics.

Batch 10 proved that the existing Morphic core can compile as real riscv64-linux-musl machine code, execute under qemu-riscv64, and produce canonical bytes identical to native hosted and fake execution. Batch 10 added zero reusable modules, zero recipes, and zero target-specific Zig semantic source files. That is the baseline to preserve.

Batch 11 must answer one narrower question:

CAN THE SAME SETTLED MORPHIC SEMANTICS EXECUTE AS A REAL FREESTANDING RISC-V PAYLOAD WHEN LINUX USERSPACE NO LONGER PROVIDES PROCESS ENTRY, STDOUT, EXIT, STACK/BOOTSTRAP, OR DEFAULT HOSTED RUNTIME BEHAVIOR?

The governing principle is:

ONE CORE.
SAME SCENARIO.
NO LINUX USERSPACE.
SMALLEST EXPLICIT MACHINE BOUNDARY.
MECHANICAL EVIDENCE.
FAIL CLOSED.

The strongest result may again be very little new code.


LONG-HORIZON DIRECTION — ALPZ, WITHOUT PREMATURELY BUILDING IT

The long-horizon operating-system direction is now explicit.

The future system, provisionally called Alpz, is intended to preserve familiar Linux/Alpine/POSIX-facing expectations while replacing increasingly more of the implementation beneath them with a Zig-native, agent-native substrate.

The desired external/internal split is:

FAMILIAR OUTSIDE.
EXPLICIT INSIDE.

Externally, future engineers and agents should reuse established concepts and interfaces wherever compatibility requires them: ELF, POSIX/Linux process and file semantics, musl expectations, sockets, mmap, signals, futexes, epoll, conventional filesystem paths, Alpine tooling, apk, and the broader Alpine package ecosystem.

Internally, the implementation should minimize Cost of Correct Use through canonical components, explicit ownership and invalidation, ordinary terminology, small dependency closures, machine-readable contracts, focused validation, precise diagnostics, and explicit unknowns.

The project is not trying to force engineers or agents to relearn solved computing conventions merely to use a new implementation.

However, Batch 11 DOES NOT implement that compatibility surface.

Do not begin:

- POSIX syscall compatibility;
- Linux syscall ABI work;
- musl integration;
- Alpine init;
- apk;
- ELF userspace loading;
- processes;
- Linux kernel boot;
- Linux guest boot;
- a new kernel;
- a hypervisor;
- virtual-memory activation;
- traps/interrupts/timers unless they become strictly necessary for this freestanding proof;
- FDT parsing;
- PLIC/CLINT;
- VirtIO;
- block/network devices;
- a universal HAL;
- a broad SBI framework.

Batch 11 is only the next machine-pressure step on the road toward that future.

Do not invent an Alpz-specific concept when an ordinary RISC-V, Zig, firmware, ELF, or emulator concept already names the thing accurately.

Do not replace a conventional standard boundary merely for purity. If OpenSBI or another normal RISC-V boundary is the smallest truthful route, use it. Novel implementation is valuable; gratuitous interface novelty is not.

PHASE 7 — FAIL CLOSED; PREVENT SILENT-FAILURE CASCADES

A machine verifier that prints plausible text while failing to prove completion is not acceptable.

The verifier must not infer success merely because expected lines appeared.

At minimum:

- enforce a finite timeout;
- timeout is failure;
- missing begin marker is failure if framing is used;
- duplicate/ambiguous begin marker is failure unless the protocol explicitly makes it impossible;
- missing end marker is failure;
- payload mismatch is failure;
- truncated payload is failure;
- unexpected extra bytes inside the canonical frame are failure;
- build/inspection failure is failure;
- emulator launch failure is failure;
- machine termination state must be interpreted only according to behavior actually demonstrated by the selected emulator/firmware route;
- do not claim a meaningful process-style exit code where none exists.

Prefer a bounded recognizable failure indication when feasible, but do not invent a large panic subsystem.

If success cannot be distinguished mechanically from a hung or partially completed machine, Batch 11 does not pass.

This is specifically intended to prevent a Silent-Failure Cascade in which later tooling accepts a false machine-success premise.
