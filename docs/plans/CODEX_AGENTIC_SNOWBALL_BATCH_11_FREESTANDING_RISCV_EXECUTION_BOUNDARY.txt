CODEX AGENTIC SNOWBALL BATCH 11 — FREESTANDING RISC-V EXECUTION BOUNDARY

MISSION

Remove Linux userspace from beneath the already-proven Morphic execution path without rewriting settled Morphic semantics.

Batch 10 proved that the existing Morphic core can compile as real riscv64-linux-musl machine code, execute under qemu-riscv64, and produce canonical bytes identical to native hosted and fake execution. That result was independently reproduced on a separate Garuda/Arch machine after merge.

Batch 11 must answer the next, narrower question:

CAN THE SAME SETTLED MORPHIC SEMANTICS EXECUTE AS A FREESTANDING RISC-V PAYLOAD WHEN LINUX USERSPACE NO LONGER PROVIDES PROCESS ENTRY, STDOUT, EXIT, STACK/BOOTSTRAP, OR PANIC BEHAVIOR?

The governing principle is:

ONE CORE.
SAME SCENARIO.
NO LINUX USERSPACE.
SMALLEST EXPLICIT MACHINE BOUNDARY.
MECHANICAL EVIDENCE.

This is not a kernel batch.
This is not an Alpine boot batch.
This is not a hypervisor batch.
This is not permission to pre-build a RISC-V platform stack.

The target outcome is one real freestanding riscv64 execution of the existing Morphic scenario under a conventional system emulator/firmware environment, with the canonical Morphic payload mechanically compared against the already-proven native output.

Do not begin Linux kernel boot, Alpine init, ELF userspace loading, processes, syscalls, virtual memory activation, traps, interrupts, timers, FDT parsing, PLIC, CLINT, VirtIO, block devices, networking, a universal HAL, a general SBI framework, or a hypervisor.

If the pressure requires only a tiny entry/output/exit adapter and zero new reusable modules, that is a strong Snowball result.

PHASE 3 — IDENTIFY THE SMALLEST FREESTANDING CONTRACT

Batch 10 established that Linux userspace currently supplies at least:

- process/program entry;
- a usable stack/bootstrap environment;
- stdout transport;
- process exit;
- hosted panic/default runtime behavior.

Batch 11 must replace only what is actually necessary to execute the canonical Morphic scenario.

Preferred architecture to test first:

QEMU system machine
    -> conventional firmware boundary, if needed
    -> tiny explicit freestanding _start / entry
    -> bounded static stack
    -> existing Morphic runFake/runCore or an equally thin target-neutral buffer machine
    -> tiny output transport
    -> explicit machine shutdown/exit

The existing recipe already exposes runCore and runFake. Prefer reusing them over creating a freestanding copy of scheduler/resource/trace behavior.

A thin freestanding adapter may be justified for:

- _start / entry symbol;
- stack establishment when required;
- static output/trace buffers;
- transporting already-produced canonical bytes to the emulator console;
- explicit shutdown after success or failure.

It must not own Morphic semantics.

PHASE 6 — PRESERVE THE CANONICAL MORPHIC PAYLOAD EXACTLY

The freestanding environment may emit firmware or emulator framing before/after our program output.

Do not compare visually.
Do not silently strip arbitrary text.

If the selected firmware emits unavoidable console noise, use explicit deterministic framing around OUR payload, for example a begin/end marker owned by the freestanding adapter. The verifier must mechanically extract only the bytes between those markers.

The bytes inside the frame must be exactly the canonical Morphic bytes produced by the shared semantics.

The markers themselves are transport framing and must never be counted as part of the canonical Morphic artifact.

Mechanically prove:

native hosted run 1 == native hosted run 2
native fake run 1 == native fake run 2
native hosted == native fake
freestanding run 1 payload == freestanding run 2 payload
native hosted canonical payload == freestanding canonical payload

If the current canonical payload is still 765 bytes, record that fact. Do not force it.

Capture raw emulator output to files.
Capture extracted payload bytes to files.
Use exact byte comparison.


PHASE 7 — FAILURE AND SHUTDOWN MUST BE MACHINE-DETECTABLE

The verifier must not infer success merely because QEMU printed expected text.

Design the smallest honest success/failure behavior available through the chosen machine/firmware boundary.

Preferred properties:

- successful Morphic run emits the complete framed payload;
- successful run requests deterministic shutdown/exit;
- failure emits a bounded, recognizable failure indication if feasible;
- the host verifier has a timeout and kills a hung emulator;
- unexpected timeout is failure;
- missing end marker is failure;
- payload mismatch is failure;
- non-success machine exit/shutdown behavior is failure where the emulator exposes a reliable status.

Do not invent elaborate panic infrastructure.
Do not claim an exit-code property the emulator/firmware cannot actually provide.
Record exact observable behavior.
