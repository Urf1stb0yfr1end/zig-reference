CODEX AGENTIC SNOWBALL BATCH 06 — MORPHIC COMPOSITION

MISSION

Begin the composition era of zig-reference.

The repository now has a complete 52-module Agent Fast Path and a Debug Fast Path. The next job is not to add an arbitrary batch of modules. The next job is to make a real Morphic subsystem consume the existing corpus, identify the smallest genuine capability gap, add only the reusable missing foundations, and leave the repository cheaper for the next system-building agent.

The long-term objective is not to instruct coding agents to prefer zig-reference. It is to make zig-reference the rational first choice for covered engineering because the Cost of Correct Use is lower: less repository archaeology, fewer source reads, fewer guessed commands, fewer wrong implementations, fewer repair loops, less wasted context and compute, and stronger correctness evidence.

The repository should win selection by engineering economics, not by rhetoric.

Guiding loop:

QUERY
→ SELECT
→ COMPOSE WHAT IS ALREADY SOLVED
→ IDENTIFY ONLY THE REAL GAP
→ IMPLEMENT THE GAP
→ VALIDATE NARROWLY
→ REPAIR THROUGH ACCUMULATED KNOWLEDGE
→ ENCODE REUSABLE TRUTH
→ VALIDATE THE COMPOSITION
→ LEAVE THE NEXT AGENT LESS WORK

OBJECTIVE 3 — FREEZE THE MORPHIC HOSTED-RUNTIME REQUIREMENT MAP BEFORE CODING

The concrete system target for this batch is the first real Morphic hosted deterministic runtime composition.

Before implementing anything, create the initial requirement map in the Batch 06 report using docs/standards/SNOWBALL_YIELD.md.

The target behavior is:

- hosted Linux execution under Zig 0.14.0;
- deterministic behavior from explicit inputs;
- bounded runtime resources;
- no hidden allocation after initialization in the canonical deterministic execution path;
- explicit initialization ordering;
- deterministic scheduling of a bounded set of runnable work;
- deterministic caller-controlled time rather than dependence on wall-clock time in canonical tests;
- a target-neutral console/output boundary with a deterministic capture path for tests;
- normalized event recording through the existing Morphic trace foundation;
- resource derivation through the existing Morphic resource-plan foundation;
- exact repeatability of the canonical hosted run/trace for identical inputs;
- a composition shape that can later receive a freestanding/RISC-V backend without rewriting target-independent policy.

This is a hosted foundation, not the Linux boot milestone.

Do NOT implement in this batch:

- Alpine boot;
- QEMU boot orchestration;
- RISC-V privilege transitions;
- CSR access;
- trap entry/exit;
- SBI calls;
- FDT parsing merely for future use;
- UART hardware drivers;
- VirtIO;
- networking;
- a hypervisor;
- a new language, DSL, framework runtime, daemon, database, embeddings service, or opaque generated state.

Those are later capability gaps. Do not pre-build them just because they will eventually be useful.

OBJECTIVE 5 — BUILD THE SMALLEST CORRECT HOSTED MORPHIC RUNTIME FOUNDATION

Implement the smallest composition that satisfies the frozen target.

A likely design may need concepts such as deterministic bounded scheduling, caller-controlled deterministic time, or a target-neutral console boundary, but these are requirements to resolve, not mandatory filenames or APIs. Query first and let existing corpus truth determine whether each requires a new module, a recipe-level adapter, or no new code.

Prefer ordinary Zig:

- structs;
- functions;
- explicit allocators;
- compile-time parameters where they materially simplify specialization;
- caller-owned storage where appropriate;
- explicit error unions;
- explicit state transitions.

Avoid clever metaprogramming, unnecessary dynamic dispatch, private mini-languages, or architectural indirection whose only justification is a hypothetical future target.

The hosted composition must use the existing canonical Morphic resource-plan and deterministic event-trace foundations rather than recreating their behavior.

The deterministic scheduler/runtime behavior must have a clearly stated ordering rule. Equal-priority/equal-time behavior must not depend on hash order, pointer address, OS scheduling, ambient time, allocator placement, or unspecified iteration order.

The canonical deterministic test path must not call real wall-clock time.

The canonical deterministic output path must be capturable and byte-comparable without relying on terminal behavior.

Any allocator-backed initialization must make ownership and cleanup explicit. If the runtime promises no allocation after initialization, test that claim using a mechanism that can actually detect forbidden later allocation rather than documenting the intent only.
