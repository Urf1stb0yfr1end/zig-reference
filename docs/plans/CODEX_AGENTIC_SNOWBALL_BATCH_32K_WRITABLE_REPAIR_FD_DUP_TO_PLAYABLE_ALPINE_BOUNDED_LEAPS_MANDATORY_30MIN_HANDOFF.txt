---------------------------------------------------------------------
REPAIR 1 — O_APPEND MUST BE TRUE OR FAIL CLOSED
---------------------------------------------------------------------

Current Batch 32J runtime-open flag handling admits Linux/RV64 O_APPEND
(asm-generic value 0x400), but the runtime resource state begins at offset zero
and runtimeRegularWrite writes at that stored offset. An existing runtime file
opened with O_APPEND can therefore overwrite its prefix instead of appending.

Required repair:

Choose the smallest correct general behavior supported by current pressure:

A. implement real append semantics, with append state owned by the open resource
   description and each write selecting the current runtime-object EOF at the
   correct semantic moment;

OR

B. reject O_APPEND at the Linux/RV64 compatibility edge until true append
   semantics are implemented.

Prefer B if real Playable Alpine pressure does not require O_APPEND during this
run. Do not accept a flag whose semantics are not actually honored.

Focused proof must establish whichever contract is chosen.

If implementing append, prove at minimum:

- existing bytes remain intact;
- the first append write begins at current EOF;
- repeated writes append rather than overwrite;
- aliases sharing one open description remain coherent;
- capacity failure leaves existing bytes coherent;
- Linux policy remains at the compatibility edge.

If rejecting append, prove at minimum:

- O_APPEND is rejected deterministically with the chosen Linux errno;
- the runtime object is not mutated;
- no resource or descriptor is leaked;
- ordinary non-append create/truncate behavior remains available.

---------------------------------------------------------------------
REPAIR 2 — RUNTIME OPEN MUST COMMIT ATOMICALLY
---------------------------------------------------------------------

Current Batch 32J ordering can call RuntimeNamespace.open(path, create, truncate)
before resource creation and descriptor binding are known to succeed.

That means a later ENFILE/EMFILE path can leave a newly created runtime object or
can truncate an existing object even though openat itself failed.

Repair this as a general bounded transaction.

Required semantics:

- before mutating runtime namespace state for create/truncate, prove that the
  required resource-description capacity and descriptor-binding capacity are
  available;
- if existing abstractions expose a clean preflight operation, reuse it;
- otherwise introduce the smallest neutral reservation/preparation mechanism
  necessary to preserve PREPARE -> COMMIT behavior;
- a failed resource allocation must not create or truncate a runtime object;
- a failed descriptor allocation/binding must not create or truncate a runtime
  object;
- capacity rejection must not leak a resource reference;
- successful open must commit exactly once;
- existing source-namespace immutability remains untouched;
- Linux errno translation remains at the Linux/RV64 edge.

Focused regressions must cover at minimum:

1. descriptor table full + O_CREAT => no new runtime object;
2. descriptor table full + O_TRUNC on an existing runtime object => existing
   bytes unchanged;
3. resource table full + O_CREAT => no new runtime object;
4. resource table full + O_TRUNC => existing bytes unchanged;
5. successful create/truncate still works after preflight;
6. no leaked resource count/reference on rejected open.

Do not solve this with pathname-specific rollback or by silently enlarging every
capacity until the test cannot reach exhaustion. Bounded exhaustion is part of
the contract.
