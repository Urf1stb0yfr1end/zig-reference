======================================================================
CURRENT FRONTIER
======================================================================

Project 59 now provides:

    ImagePage
    MaterializedImage(page_capacity)
    MaterializedImage.prepare(bytes, load_plan, bias)
    MaterializedImage.items()

The materializer:

- walks every validated load segment;
- produces complete 4 KiB page images;
- handles non-page-aligned segment geometry;
- copies exact file-backed bytes;
- zero-fills BSS and untouched fresh-page bytes;
- merges shared-page contributions;
- composes final permissions;
- rejects W+X;
- fails explicitly on source/overflow/capacity errors;
- touches no live page tables or physical frames while preparing the image.

That closes the neutral image-construction mechanism.

The next real blocker is MACHINE INTEGRATION.

The freestanding RV64 runtime still has a tiny historical proof-fixture backing
shape, including:

    const physical_pool_pages = 8;

and the current real-exec path has not yet consumed the full MaterializedImage
page set as a staged physical/Sv39 image.

Do not reopen the materializer unless a real test demonstrates a defect.
Do not replace it with a BusyBox-specific loader.

======================================================================

The research objective is not "make BusyBox work at any cost."

Real software discovers needs.
Historical compatibility does not automatically define permanent architecture.

Before adding a permanent Morphic primitive, answer:

2. Why can it not remain in the Linux/ELF compatibility edge?
3. Could a non-Linux system naturally reuse it?

======================================================================
3. PREPARE ALL MACHINE RESOURCES BEFORE DESTRUCTIVE EXEC COMMIT
======================================================================

Batch 26 established an important invariant:

    ordinary failure occurs before destructive replacement

Preserve it.

The machine PREPARE phase should, as applicable, complete or reserve:

- exact external bytes and identity;
- complete ExecPlan / LoadPlan validation;
- complete MaterializedImage construction;
- exact page count;
- checked guest virtual ranges;
- all required physical backing frames;
- page-table capacity / required intermediate tables;
- final page permissions;
- stack/start state;
- any ordinary fallible bookkeeping needed by COMMIT.

If any ordinary preparation fails, release every newly reserved resource and
leave the current live image intact.

Do not allocate page 37 after destroying Program A if that allocation can fail.
Do not leak frames on partial preparation.
Do not leave partially installed mappings on failure.

COMMIT should be deliberately small and deterministic.

======================================================================
4. PHYSICAL BACKING: FIX THE REAL CAPACITY PROBLEM, NOT THE NUMBER 8
======================================================================

Current freestanding code contains a small historical proof pool:

    const physical_pool_pages = 8;

Real external images may require substantially more image backing and may also
require page-table frames.

Do not simply increase 8 to an arbitrary huge magic constant and declare the
problem solved.

First measure from the exact artifact and the actual Sv39 mapping path:

- image pages required;
- existing page-table frames required;
- additional page-table frames required;
- stack/other persistent user pages;
- temporary versus committed ownership;
- cleanup requirements.

Then implement the smallest general bounded backing strategy appropriate to the
machine proof.

It is acceptable to introduce a larger explicit bounded arena or cleanly
separate image backing from page-table backing if that is the smallest neutral
solution supported by the evidence.

It is NOT necessary in Batch 28 to build demand paging, swapping, a page cache,
a full VM subsystem, or an unbounded allocator merely because BusyBox is large.

Preserve existing small focused allocator/page-table proofs where possible.

======================================================================
5. INSTALL EVERY MATERIALIZED PAGE WITH FINAL PERMISSIONS
======================================================================

Consume MaterializedImage.items() generically.

For every prepared page:

- associate it with owned physical backing;
- copy the exact 4096 prepared bytes into the backing frame;
- install the mapping at page.virtual_start;
- translate the materializer permission record to the machine Sv39 permission
  representation without widening it;
- maintain U/S permission truth;
- reject W+X;
- make shared-page composition match the already-prepared neutral page image;
- execute required sfence.vma operations;
- execute fence.i before newly materialized executable bytes are entered.

Do not create a user RWX population window for convenience.
Populate through supervisor-owned physical access and install final user
permissions.

The machine adapter may know Sv39.
The neutral MaterializedImage must not become Sv39-specific.
