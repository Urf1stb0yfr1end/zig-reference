CODEX AGENTIC SNOWBALL BATCH 09 — MORPHIC MACHINE OPERATIONS

MISSION

Begin the next system-expansion phase by giving Morphic one small target-neutral machine-operations boundary and proving that the same core runtime logic can execute through more than one implementation without becoming more than one implementation.

Batch 06 established the hosted deterministic Morphic runtime and explicitly identified the next smallest frontier as a target-neutral machine-operations interface plus a deterministic fake adapter before attempting a privileged RISC-V backend.

Batch 07 established Correct-Use Preflight.
Batch 08 established Invariant-Guided Diagnosis.

Batch 09 must now use those foundations while expanding the system.

The governing idea is:

ONE CORE RUNTIME.
MULTIPLE MACHINE IMPLEMENTATIONS.
NO SECOND SEMANTIC IMPLEMENTATION.

This batch is not about making a large abstraction framework. It is about finding the smallest ordinary Zig boundary that isolates machine-specific operations from the already-working bounded deterministic runtime.

The machine boundary must be cheap for a coding agent to discover, inspect, satisfy, validate, and diagnose.

Do not begin Alpine.
Do not begin Linux boot handoff.
Do not begin a privileged RISC-V CSR/trap/SBI implementation.
Do not begin UART, FDT, PLIC, CLINT, VirtIO, networking, or a hypervisor.
Do not create a universal HAL.
Do not create a new DSL, interface language, macro system, daemon, database, source scanner, or compiler substitute.
Do not create speculative machine operations merely because future systems might someday need them.

Build only the boundary demonstrated by real current composition pressure.

ARCHITECTURAL OBJECTIVE 1 — THE SMALLEST MACHINE-OPERATIONS BOUNDARY

Derive the machine-specific boundary from operations the current Morphic scenario actually needs.

The boundary should answer a narrow question:

"What must the core runtime ask a machine implementation to do, while everything else remains target-neutral?"

Prefer ordinary Zig structure and compile-time composition. Do not invent runtime dynamic dispatch unless actual requirements justify it.

Potential operation classes include output and caller-controlled logical time only if the current runtime genuinely needs them through the machine boundary. These examples are not mandates.

Do not add speculative operations for:

- interrupts;
- page tables;
- privilege changes;
- CSRs;
- SBI;
- MMIO;
- UART;
- FDT;
- disks;
- networking;
- allocation;
- threading;
- wall-clock time;
- shutdown/halt;

unless the existing Batch 09 scenario provides concrete, tested need. Future usefulness is not sufficient evidence.

The boundary must keep important semantics visible:

- ownership;
- borrowing;
- cleanup;
- allocation behavior;
- boundedness;
- error/failure behavior;
- determinism;
- state transitions;
- invalidation where relevant;
- environment assumptions;
- exact validation.

If an operation can fail, expose the failure honestly. Do not swallow it behind a convenience wrapper.

If no standalone reusable module is needed, keep the boundary in the smallest canonical composition location and explain why a module would have added unnecessary surface area.

If actual pressure demonstrates a generally reusable standalone mechanism, create the minimum module that satisfies it and give it the full repository contract, Agent Fast Path, tests, diagnostics/evidence where justified, and command registration required by AGENTS.md.

ARCHITECTURAL OBJECTIVE 2 — DETERMINISTIC FAKE MACHINE

Add a deterministic fake machine implementation that satisfies the same machine-operations boundary used by the hosted implementation.

The fake exists to make machine behavior cheap to test without operating-system I/O or a future hardware backend.

It must be deliberately boring:

- deterministic;
- bounded where the exercised operation is bounded;
- no network;
- no wall clock;
- no hidden global state;
- no hidden post-initialization allocation unless canonical requirements make it unavoidable;
- caller-controlled or fixed state where appropriate;
- explicit failure for exhausted caller-provided capacity when that boundary exists;
- easy to instantiate in a focused test;
- easy for a coding agent to understand from the compact contract/preflight surface.

Do not turn the fake into a simulator for RISC-V hardware.
Do not model devices that the Batch 09 scenario does not use.

The fake should be useful as a future semantic oracle for real machine implementations, but Batch 09 must not claim cross-target equivalence before such a target exists.

ARCHITECTURAL OBJECTIVE 3 — ONE CORE RUNTIME, TWO IMPLEMENTATIONS

Refactor only as necessary so one canonical runtime/composition path can execute against:

1. the existing hosted implementation; and
2. the deterministic fake implementation.

Do not copy the scheduler/resource/trace orchestration into two implementations.
Do not create hosted_core.zig and fake_core.zig copies of the same runtime logic.
Do not duplicate canonical task scheduling policy, resource planning, trace semantics, or output formatting.

The machine implementations may differ only where the machine boundary requires them to differ.

The test must make duplication visible. Prefer a single generic/comptime core function instantiated with both implementations over two similar functions maintained separately, if that is the cleanest Zig 0.14.0 design.

Prove, for the same canonical input scenario, every equivalence that is actually meaningful and observable.

At minimum investigate:

- normalized event trace equality;
- captured logical output equality;
- deterministic ordering equality;
- explicit failure behavior for a bounded output/capacity condition if applicable.

Only claim byte-for-byte equivalence for artifacts actually compared byte-for-byte.

Do not claim machine equivalence beyond the tested observable surface.

ARCHITECTURAL OBJECTIVE 6 — PREPARE, DO NOT IMPLEMENT, THE RISC-V DIFFERENCE

The Batch 09 result should leave a future RISC-V implementation with a narrow visible target-specific surface.

Record in the Batch 09 report:

- the exact machine operations a future implementation would need to satisfy for the tested scenario;
- which current semantics remain entirely target-neutral;
- which future RISC-V concerns are intentionally outside the current boundary;

This is not a promise that all architecture differences will remain small. It is an explicit boundary for the semantics demonstrated so far.

CORRECTNESS AND CODE QUALITY

The purpose of this repository is not to win agent preference by slogans. Make the implementation the rational choice by being cheaper to discover, safer to reuse, easier to validate, and clearer to repair.

For all new or changed code:

- prefer simple ordinary Zig over clever metaprogramming;
- keep interfaces minimal;
- make ownership and resource use explicit;
- avoid hidden allocation;
- avoid hidden ambient state;
- preserve deterministic behavior;
- keep error sets truthful;
- preserve failure atomicity where the existing contract promises it;
- test boundaries and negative paths;
- use exact public symbols in examples;
- keep compiler output authoritative;
- do not add abstraction layers with only one demonstrated reason to exist;
- do not optimize for line count at the expense of correctness;
- do optimize the agent-facing representation for high information density.

The best compact representation is the smallest one that preserves the facts required for a correct decision.

Do not make intelligence pay twice for settled engineering knowledge.
