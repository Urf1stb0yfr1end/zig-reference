BATCH 22 SCOPE DECISION

Keep the first ELF artifact intentionally tiny.

Preferred Batch 22 proof shape:

- one independently built RV64 ELF executable artifact;
- static/freestanding, no PT_INTERP;
- no libc;
- no relocations required at runtime;
- one minimal executable PT_LOAD segment is sufficient for this batch;
- e_entry lies inside that executable PT_LOAD segment;
- use the already-proven user stack mapping rather than inventing Linux process-startup stack semantics;
- the loaded program executes a deterministic marker/check and one deliberate ECALL;
- the ECALL returns through the existing trusted supervisor boundary to a known S-mode continuation.

A second writable PT_LOAD segment is NOT required merely to make Batch 22 look more complete. If the smallest truthful fixture can prove real ELF execution with one RX PT_LOAD plus the already-existing user stack, prefer that bounded proof. Multi-segment/writable-data/startup-stack pressure can become Batch 23 unless implementation reality proves it is inseparable.

REAL ELF ARTIFACT REQUIREMENT

The program executed in Batch 22 must be a real ELF file produced as a distinct build artifact.

It must not be represented only as:

- a byte array hand-authored inside freestanding_riscv64.zig;
- a copied kernel .text template masquerading as an ELF load;
- machine-emitted expected constants with no independently inspectable ELF truth.

Do not commit generated ELF binary artifacts to the repository unless existing repository policy explicitly permits it. Prefer deterministic build-time production of the tiny RV64 fixture and deterministic inclusion/availability to the Alpz execution lab.

The external verifier must be able to inspect the actual guest ELF with readelf or equivalent repository-approved tooling independently of Alpz runtime claims.

ELF ACCEPTANCE BOUNDARY

Use the canonical Z-Ref ELF parsers.

Batch 22 must mechanically validate at least the subset required for the chosen tiny fixture, including:

- ELF magic;
- ELF64 class;
- little-endian encoding if that is the supported RV64 machine contract;
- supported ELF version;
- RISC-V machine identity;
- supported executable type for this fixture;
- program-header table bounds/count/entry size through existing parser contracts;
- bounded PT_LOAD discovery;
- p_offset + p_filesz bounds within the ELF artifact;
- p_filesz <= p_memsz;
- checked virtual-range arithmetic;
- required alignment relationship for the chosen load contract;
- e_entry contained in an executable loaded range;
- no unsupported overlapping load layout for this bounded proof;
- permission flags translated truthfully rather than widened for convenience.

Do not silently accept unsupported ELF features. Reject them deterministically and document the narrow supported subset.

If the existing parser exposes a different exact vocabulary or stronger checks, use its canonical contract rather than duplicating parallel validation.

LOAD / MAPPING POLICY

Prefer reuse of the already-proven user address-space geometry where it keeps the proof smaller and truthful.

Established addresses include:

user code VA:
0x80401000

user stack VA:
0x80402000

user stack top:
0x80403000

For the preferred minimal Batch 22 fixture, arrange the actual guest ELF so its executable PT_LOAD is loadable at the existing U RX code region and its e_entry is inside that segment.

Reuse the existing allocator-owned user code frame and existing U RW/NX stack frame if doing so preserves truthful ELF semantics and keeps Batch 21 invariants intact.

Do not allocate or remap additional pages merely to demonstrate allocation growth.

If translation/PTE mutation is genuinely unnecessary because the ELF is loaded into already-correct U RX geometry, preserve that fact and report it accurately.

If the real ELF contract requires a mapping change, use the existing Sv39 builder/invalidation machinery and mechanically prove the exact change. Never emit decorative SFENCE.VMA claims.

Executable bytes copied into an already-mapped physical code frame require the appropriate local FENCE.I before user instruction fetch.

PERMISSIONS

Batch 22 must never create W+X.

For every ELF PT_LOAD range actually used:

- derive permissions from the real ELF program-header flags;
- reject or safely handle flag combinations outside the deliberately supported Batch 22 subset;
- require U=1 for userspace mappings;
- executable program bytes must not become writable merely because copying them was convenient;
- writable data, if any is admitted by the chosen minimal fixture, must be NX.

The verifier must reconstruct permission truth from actual raw PTE evidence rather than trusting labels printed by the kernel.

COPY / ZERO-FILL SEMANTICS

For each supported PT_LOAD segment:

- copy exactly p_filesz bytes from the ELF artifact;
- if p_memsz > p_filesz is supported in Batch 22, zero exactly the tail and prove it;
- never read outside the ELF artifact;
- never write outside the planned segment memory range;
- keep arithmetic checked;
- preserve failure atomicity as far as the bounded design permits.

If BSS-style p_memsz > p_filesz is not needed for the smallest Batch 22 fixture, it may be rejected/deferred explicitly rather than half-implemented.

Do not turn Batch 22 into a full Linux exec loader.

ENTRY / USER EXECUTION

The user entry PC must come from the parsed ELF e_entry.

Do not enter a hard-coded probe address and merely print that it equals e_entry.

The external verifier must independently inspect the guest ELF entry and load segment(s), then compare those facts against runtime evidence.

Enter U-mode through the already-proven privilege transition path.

Preserve:

- SPP=0 for U entry/return;
- SUM=0;
- trusted supervisor trap stack;
- csrrw sp,sscratch,sp as the first user-origin trap-entry instruction before trap-frame memory stores;
- bounded interrupt policy used by the existing proof;
- correct sscratch rearming where U-mode return requires it;
- deliberate stvec/sscratch restoration when the proof returns to supervisor continuation.

TINY GUEST PROGRAM

Keep the first guest program deliberately simple and independently inspectable.

It should:

1. begin at its ELF e_entry;
2. execute real RV64 U-mode instructions loaded from the ELF PT_LOAD segment;
3. use the already-proven user stack in a bounded way if useful;
4. place one deterministic terminal marker in a register and/or stack location;
5. execute one deliberate ECALL;
6. have a fail-stop path so accidental continuation cannot masquerade as success.

This ECALL is a bounded proof signal, not a Linux syscall ABI.

Do not assign it a Linux syscall number merely to make the demo look Unix-like.
