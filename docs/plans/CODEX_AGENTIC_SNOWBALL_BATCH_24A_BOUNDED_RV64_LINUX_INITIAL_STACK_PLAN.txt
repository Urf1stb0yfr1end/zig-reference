MISSION

Batch 23 proved a real separately built RV64 ET_EXEC userspace ELF with one R-X PT_LOAD plus one RW- PT_LOAD containing initialized data and non-empty BSS can be loaded, mapped, executed in real U-mode, mutated, and returned through the trusted supervisor boundary under strict QEMU evidence.

Batch 24 begins the initial Linux-process-startup boundary.

This boundary is deliberately split because it contains two distinct truths:

24A — define and mechanically validate the reusable bounded RV64 Linux initial-stack image/layout contract without QEMU or kernel mutation.

24B — later consume that settled planner in Alpz, materialize the planned bytes into real mapped user-stack memory, enter the ELF with the planned SP, and prove real U-mode observation of argc/argv/envp/auxv under strict QEMU evidence.

Batch 24A must prove exactly one new reusable fact:

A bounded, allocation-free, failure-atomic planner can construct the complete byte image and exact address relationships for a deliberately narrow RV64 Linux-style initial userspace stack containing argc, argv, envp, a bounded auxiliary vector, NUL-terminated strings, required sentinels, and a 16-byte-aligned initial stack pointer, without writing guest memory and without depending on page tables, QEMU, ELF execution, or kernel orchestration.

The decisive new fact is:

Linux-style process startup stack semantics become a reusable machine-readable planning primitive before Alpz performs any machine-side stack construction.

AUTHORITATIVE ABI SHAPE

The implementation must model the deliberately bounded Linux/RV64 startup shape, not invent a private Alpz startup convention.

Use primary ABI/source truth when resolving ambiguity. The relevant shape is the Linux ELF process startup contract and the RISC-V psABI requirement that the stack pointer be 128-bit / 16-byte aligned at procedure entry.

For this batch, the planned initial stack at final SP must have the conventional downward-growing RV64 word layout:

lowest address / initial SP

    argc                         one 64-bit word
    argv[0]                      64-bit pointer
    argv[1]
    ...
    argv[argc-1]
    NULL                         64-bit zero sentinel
    envp[0]                      64-bit pointer
    envp[1]
    ...
    NULL                         64-bit zero sentinel
    auxv[0].type                 64-bit word
    auxv[0].value                64-bit word
    auxv[1].type
    auxv[1].value
    ...
    AT_NULL                      64-bit zero
    0                            64-bit zero
    zero padding as needed
    NUL-terminated argv/env strings in deterministic planned locations

higher address / bounded stack top

The exact deterministic string packing direction/order may be selected by the module, but it must be documented, stable, non-overlapping, and mechanically tested.

The final initial SP must be 16-byte aligned.

All argv/envp pointers emitted into the image must point to the exact corresponding NUL-terminated bytes inside the same planned stack image.

The planner must append required argv/envp NULL sentinels and the terminating AT_NULL pair itself. Callers must not be able to accidentally omit them.

This is a deliberately narrow Linux-compatible startup image contract, not a claim to reproduce every current Linux create_elf_tables feature.

ARGV REQUIREMENTS

The planner must support a deliberately bounded nonzero argv vector.

For each argument:

- input is a byte string without an interior NUL;
- planner appends exactly one NUL terminator;
- planner assigns one exact in-image guest virtual address;
- argv table contains that address exactly once in order;
- argv[argc] is a zero pointer;
- argc equals the exact argv count;
- no pointer may refer outside the returned used stack image;
- no string regions may overlap table words or one another.

For the first contract, requiring argc >= 1 is acceptable and arguably preferable because Linux process argv normally includes argv[0]. If zero-argc support is intentionally admitted, document and test it explicitly rather than allowing it accidentally.

ENVIRONMENT REQUIREMENTS

The planner must support a bounded envp vector.

For each environment string:

- no interior NUL;
- exactly one appended NUL;
- deterministic placement;
- exact pointer in the envp table;
- one final zero pointer after the last envp entry.

An empty environment must be a valid, explicitly tested case if the implementation can represent it cleanly.

Do not parse NAME=VALUE semantics in this batch. The planner lays out environment strings; it does not define shell/environment policy.

AUXILIARY VECTOR REQUIREMENTS

Batch 24A must establish the structural auxv contract without prematurely implementing the entire Linux auxiliary-vector universe.

The planner must support a bounded ordered list of 64-bit type/value entries and append the terminal:

    AT_NULL = 0
    value   = 0

itself.

Reject caller-supplied AT_NULL if allowing it would make termination ambiguous.

Prefer rejecting duplicate auxv types for this first bounded contract unless primary Linux behavior or a strong future requirement makes duplicates necessary. If duplicates are admitted, document exact ordering/lookup semantics and test them.

The planner must be able to represent at least the kinds of immediate values needed by the later Batch 24B fixture, conceptually including a minimal subset such as:

- AT_PAGESZ;
- AT_ENTRY;
- AT_UID;
- AT_EUID;
- AT_GID;
- AT_EGID;
- AT_SECURE.

If a tiny symbolic value form can cleanly and generally resolve an aux entry to the planned argv[0] string, support it so a future Batch 24B may truthfully emit AT_EXECFN without a second layout pass.

Do NOT add AT_PHDR merely by hardcoding a value if the relevant program-header bytes are not actually mapped in the future process image.

Do NOT add AT_RANDOM unless the planner has a truthful bounded representation for the referenced 16-byte payload.

Do NOT fabricate HWCAP, HWCAP2, VDSO/SYSINFO_EHDR, platform strings, interpreter base, clock tick, rseq, or other auxiliary values merely to make the vector look realistic.

This module plans structure; caller policy chooses truthful aux entries.

STACK RANGE / ALIGNMENT REQUIREMENTS

The caller supplies a checked bounded guest stack virtual range or equivalent top/bottom truth.

The planner must:

- reject non-representable address arithmetic;
- reject an invalid or empty stack range when it cannot hold the required image;
- place the entire used image within the caller-provided stack range;
- keep final initial_sp aligned to 16 bytes;
- ensure every table word is naturally 8-byte aligned;
- ensure all generated pointer values are exact guest virtual addresses;
- ensure strings and table regions do not overlap;
- deterministically zero alignment/padding bytes in the returned image;
- never wrap addresses while subtracting/adding sizes.

Do not silently truncate addresses, lengths, counts, or pointer values.

FAILURE ATOMICITY

At minimum include explicit error behavior for:

- output capacity exhausted;
- stack range too small;
- address arithmetic overflow/underflow;
- too many argv entries for the selected bound;
- too many envp entries for the selected bound;
- too many auxv entries for the selected bound;
- interior NUL in argv/envp strings;
- caller-supplied AT_NULL if forbidden;

The implementation must construct into local owned state and only return success after the complete image and every relationship validate.
