A1. MANDATORY COMMAND MANUAL RULE

Every Codex run that changes the repository must update COMMANDS.md before completion.

This is standard repository behavior, not a Batch 04-only instruction.

The AGENTS.md rule must state the equivalent of:

- Add every new runnable command introduced by the run.
- Update changed commands, arguments, purposes, or validation status.
- Remove or accurately mark obsolete commands.
- If the command surface itself did not change, still update COMMANDS.md with validation/workflow information materially established by the run.
- Never document a command that does not actually exist.
- Never call a command validated unless it actually executed successfully in the reported environment.
- Before completion run:

  PYTHONDONTWRITEBYTECODE=1 python3 tools/check-command-reference.py --check

- COMMANDS.md must be current when the run finishes.

Do not merely mention this in the Batch report. Persist it in AGENTS.md.

A2. DEVELOPER MINIMUS STANDARD

Persist the Minimus as a repository-wide developer convention in AGENTS.md.

The Minimus is for any serious developer, not merely coding agents.

IMPORTANT: existing command output MUST remain available as it is today. The Minimus is APPENDED after the normal output has finished. It is not a replacement, simplification, suppression, or rewrite of existing test/build/doctor output.

For serious developer-facing health, smoke, doctor, verification, validation, or diagnostic entry points, the successful terminal tail should follow this conceptual order:

NORMAL EXISTING OUTPUT
... unchanged existing command output ...

LOCATIONS
<small bounded set of useful clickable locations>

MINIMUS
<compact developer handoff summary>

The Minimus plus Locations block must be appended at the end.

Define “serious developer-facing” narrowly enough not to pollute every tiny unit test. It includes aggregate or diagnostic commands whose purpose is to answer whether a meaningful repository/subsystem state is healthy or to give a developer a substantial debugging handoff. Examples include repository doctor, aggregate smoke/validation, Morphic verification, and dedicated diagnostic/support flows. A tiny focused module unit test does not need Minimus merely because it is runnable.

The Minimus must be 200 lines or fewer. It should normally be far shorter.

A useful Minimus contains only the essence required for a developer to continue:

- PASS / FAIL / PARTIAL status;
- exact command/subsystem checked;
- important counts or boundaries;
- what materially succeeded or changed;
- warnings/failures that matter;
- exact next focused command or repair path when action is needed;
- branch, commit, Zig version, target, or environment only when materially useful.

Do not dump raw logs into Minimus.
Do not repeat hundreds of passing test lines.
Do not hide existing output.
Do not turn Minimus into a second verbose report.

A3. LOCATIONS MUST BE NAVIGABLE

Immediately above MINIMUS, serious developer summaries must print a LOCATIONS block.

LOCATIONS is a bounded navigation aid, not a repository listing.

Each location should point to an existing path directly relevant to understanding or repairing the run, such as:

- canonical source;
- canonical details.json or contract;
- generated index/report;
- diagnostic report;
- recipe/integration file;
- command-created log file when one exists.

Locations shown in the console must be clickable where ordinary developer terminals support it.

Use a durable literal file URI as the baseline representation:

file:///absolute/path/to/relevant/file

The implementation may additionally emit OSC 8 clickable labels when stdout is an interactive terminal, but the literal file:// URI must remain available as a fallback. Do not make correctness depend on OSC 8 support.

Do not hard-code one developer's home directory. Resolve paths from the current repository/worktree and current log destination.

If a serious diagnostic command already writes a .txt diagnostic/log file, append the same LOCATIONS + MINIMUS handoff to the text log as well as the console so the saved artifact carries its own navigation and summary.

Do NOT start creating log files for every command merely to satisfy this rule. Preserve existing logging behavior. The requirement is: when such a diagnostic .txt exists, its tail should carry the same developer handoff.

A4. MINIMUS MUST BE DETERMINISTIC AND CHEAP

Prefer deriving Minimus facts from information the command already computed.

Do not rescan the entire repository solely to create the summary when the result is already known.

Keep key ordering stable so diffs and saved logs are easy to compare.

Avoid timestamps unless the parent command already has a legitimate reason to record one.

A Minimus must never turn a failing command into success or mask a nonzero exit code.

If a wrapper controls a recognized failure path and can safely append a failure Minimus before returning the original nonzero status, do so. Do not redesign the entire Zig build graph solely to guarantee a Minimus after catastrophic tool/process termination.
