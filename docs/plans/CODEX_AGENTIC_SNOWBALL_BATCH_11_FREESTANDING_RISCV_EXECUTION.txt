CODEX AGENTIC SNOWBALL BATCH 11 — FREESTANDING RISC-V EXECUTION

MISSION

Remove Linux userspace from beneath the already-settled Morphic execution path without rewriting Morphic semantics.

Batch 10 proved that the same Morphic runCore can execute as native hosted code, through the deterministic fake machine, and as real riscv64-linux-musl machine code under QEMU user-mode while producing byte-identical canonical output.

Batch 11 must answer the next smaller and harder question:

CAN THE SAME MORPHIC SEMANTIC CORE EXECUTE AS A FREESTANDING RISCV64 PAYLOAD UNDER A CONVENTIONAL SYSTEM EMULATOR, WITH NO LINUX USERSPACE, WHILE PRESERVING THE SAME CANONICAL OBSERVABLE BYTES?

ONE CORE.
NO LINUX USERSPACE.
MINIMAL BOOTSTRAP.
MINIMAL MACHINE/FIRMWARE BOUNDARY.
MECHANICAL BYTE EVIDENCE.
NO SECOND SEMANTIC IMPLEMENTATION.

This is not a kernel batch.
This is not an Alpine batch.
This is not a hypervisor batch.
This is the smallest honest pressure that removes the Linux process/runtime layer from the Batch 10 proof.

PREFERRED EXECUTION SHAPE

Prefer a conventional riscv64 system-emulation path using QEMU virt and a small freestanding Zig payload.

A firmware-assisted launch through OpenSBI is explicitly permitted if it is the smallest conventional path available in the environment. In that case OpenSBI is external execution infrastructure, not Morphic semantic truth.

A reasonable target shape is:

QEMU system emulator
-> conventional RISC-V firmware boundary, if needed
-> freestanding riscv64 Zig entry/bootstrap
-> the existing Morphic runCore
-> bounded output storage
-> minimal transport of the canonical payload
-> deterministic shutdown/termination

Do not assume the exact implementation before discovery. If a simpler conventional freestanding path exists in the supplied environment, use it only after recording why it is smaller and equally truthful.

The preferred Zig target is a freestanding riscv64 target such as riscv64-freestanding-none if that is the actual Zig 0.14.0 spelling supported by the toolchain. Discover the real target spelling mechanically; do not force a guessed string from this document.

PHASE 3 — ATTEMPT THE CHEAPEST FREESTANDING COMPILE

The first implementation question is not "what RISC-V subsystem should we build?"

It is:

WHAT IS THE SMALLEST BOUNDARY REQUIRED TO CALL THE EXISTING runCore WITHOUT A LINUX PROCESS?

Attempt to reuse the existing target-neutral Morphic implementation directly.

A target-specific freestanding root may import the same core. It may perform only machine-boundary responsibilities such as:

- establish any required stack/bootstrap;
- construct or reuse a bounded machine/output buffer;
- call runCore;
- transport the resulting canonical bytes;
- terminate/reset in a deterministic way.

Forbidden:

- copying runCore;
- copying scheduler policy;
- copying resource planning;
- copying trace semantics;
- copying task ordering;
- reformatting the canonical Morphic artifact separately for RISC-V;
- a second canonical scenario encoded in the freestanding root.

If the existing FakeMachine or another current bounded machine can compile freestanding and provide the exact in-memory output boundary, reuse it rather than creating a near-copy.

If a hidden hosted assumption prevents freestanding compilation, classify it before repair:

- stdlib dependence;
- process/stdout dependence;
- allocation dependence;
- panic/runtime dependence;
- target/configuration issue;
- architecture-width assumption;
- other known invariant;
- unknown.

Repair shared code only when the repair is genuinely target-neutral and evidence-backed.

PHASE 4 — MINIMAL ENTRY, STACK, LINK, TRANSPORT, EXIT

Implement only what the freestanding execution actually requires.

ENTRY / STACK

Discover the actual entry contract of the chosen system-emulation/firmware path. Do not assume Linux process startup.

If the environment/firmware does not establish a usable Zig stack, provide the smallest explicit static stack/bootstrap required to enter ordinary Zig code safely.

Keep startup code tiny and auditable.
Do not build a generic boot framework.

LINK PLACEMENT

Use a tiny linker script or Zig build configuration only if required by the chosen QEMU/firmware loading contract.

Record the load/entry address and how it was derived from the actual execution environment.
Do not cargo-cult an address without evidence.

OUTPUT TRANSPORT

The Morphic canonical artifact must remain the output of the existing semantic core.

Firmware/emulator text may appear before or after the program payload. If so, add deterministic transport framing outside the canonical Morphic bytes, for example a short BEGIN marker and END marker, solely so the verifier can mechanically extract the payload.

The verifier must compare the extracted payload bytes exactly against native canonical bytes.
Do not normalize whitespace, newlines, numbers, or trace content.
Do not treat visual similarity as equality.

If firmware calls are used for console output, implement the smallest truthful call boundary. Do not build a full SBI abstraction unless current execution pressure actually justifies reusable structure.

EXIT / SHUTDOWN

Prefer a deterministic firmware or emulator-supported shutdown/reset mechanism over hanging forever and relying on a human to kill QEMU.

A timeout may exist as a verifier safety bound, but timeout termination alone should not be treated as successful program completion when a conventional deterministic shutdown path is available.

Record exactly how completion is signaled and how the verifier distinguishes success from failure.

PANIC / FAILURE

Do not silently rely on Linux panic behavior.
If freestanding Zig requires an explicit panic boundary, make it minimal and deterministic.
If runCore fails, produce a mechanically distinguishable failure result and ensure the verifier fails.
