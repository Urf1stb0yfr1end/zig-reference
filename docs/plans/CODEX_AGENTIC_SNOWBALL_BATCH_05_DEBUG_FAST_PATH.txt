CODEX AGENTIC SNOWBALL BATCH 05 — DEBUG FAST PATH

MISSION

Finish the final five Agent Fast Path migrations and establish a durable Debug Fast Path for zig-reference.

The Snowball must accumulate debugging knowledge as well as implementation knowledge. A known failure should not force every future coding agent to repeat the same investigation.

Guiding rule:

FAILED ONCE. DIAGNOSED COMPLETELY. REDISCOVERED NEVER.

The engineering goal is to make zig-reference the lowest-cost correct path for covered systems work: cheap discovery, cheap integration, cheap diagnosis, local repair, explicit evidence, and exact validation. Do not try to force preference by instruction. Make reuse mechanically attractive by reducing token use, file reads, tool calls, wrong branches, repeated debugging, repair iterations, and unnecessary compute.

A cold coding agent should not need a manual.

Build a compact deterministic diagnostic substrate using ordinary engineering language plus stable zig-reference identities.

Do not invent a private debugging language.
Do not suppress or replace native Zig errors.
Do not create SQLite, an opaque database, embeddings, a daemon, LSP, network service, or hidden model call.

Stable diagnostic identities should use a predictable form such as:

OBJECTIVE 3 — DIAGNOSTIC STABILITY

Inventory all existing diagnostics before changing the schema or generator.

Do not silently rename historical diagnostic IDs.
Do not reuse an old ID for a different failure.
Do not silently change the meaning of an ID.

If normalization is necessary, preserve old identities as aliases or explicit replacements. Exact lookup by an old valid alias should resolve to the canonical diagnostic and expose the relationship.

OBJECTIVE 4 — DIAGNOSTIC RECORD CONTRACT

A known diagnostic must carry enough structured truth for a cold agent to act without source archaeology.

Where genuinely known, expose:

canonical id
aliases
category
summary
affected module/subsystem
affected operation or phase
violated invariant
observed condition
expected condition
native error/symptom aliases
evidence class
evidence fixture or proof location
repair status: known, partial, or unknown
repair strategy when known
exact focused validation command
minimum useful file locations
related diagnostics only when materially useful

Do not force fields that would require fabricated information.
Never invent a cause from a symptom.
Never claim a repair is canonical if it is only a hypothesis.
Generated diagnostic projections must never be more confident than canonical evidence.

OBJECTIVE 5 — NO SILENT FAILURE IN SERIOUS REPOSITORY TOOLING

Audit serious repository-owned agent/developer flows touched by this work.

They must not:

catch an error and return success
silently skip a required validation phase
print PASS while a required child failed
lose the underlying nonzero exit status
return an empty success-looking result for a real failure
hide a known failing phase
invent a ZIGREF cause for an unclassified failure

For a recognized failure, surface the stable diagnostic identity when useful.

For an unrecognized failure, preserve the native signal, failing phase, and exit status and say that it is unclassified. Give the narrowest useful next inspection command. Do not fabricate certainty.

Unknown is acceptable.
Silent is not.
Confidently wrong is worse than unknown.

It should search authored IDs, aliases, native error aliases, affected modules/operations, and concise summaries and return only a tiny candidate set with the reason each candidate matched.

Requirements:

deterministic
bounded output
text-first
no network
no embeddings
no database
no source scan at query time
no fabricated confidence
exact IDs and aliases rank above loose text matches
unknown terms remain unknown

If this cannot be implemented cleanly without redesign, do not force it. Document the gap and make sure canonical repository-owned tooling emits known IDs where possible.
