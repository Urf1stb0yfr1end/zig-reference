SUPPORTED FIRST ELF SUBSET

The plan must encode an explicit narrow first userspace subset suitable for Batch 22B.

At minimum, the composition must be able to require and validate:

- ELF magic;
- ELF64 class;
- little-endian data encoding;
- supported ELF identification/version;
- RISC-V machine identity;
- a deliberately supported executable type for the first fixture;
- bounded program-header table/count/entry size through canonical parsers;
- at least one PT_LOAD;
- bounded PT_LOAD file range;
- p_filesz <= p_memsz;
- checked virtual-memory range arithmetic;
- coherent supported alignment relationship;
- deterministic permission translation from ELF PF_R/PF_W/PF_X truth;
- no accepted W+X load segment for this first policy;
- e_entry contained in an executable admitted PT_LOAD memory range;
- unsupported overlapping PT_LOAD layouts rejected unless a simple, explicitly correct non-overlap policy already exists;
- unsupported features rejected explicitly rather than silently ignored.

Do not claim a complete System V or Linux ELF loader.

Do not add support merely because ELF permits something if Batch 22B does not need it yet.

LOAD-PLAN CONTRACT

The output must be a complete immutable/failure-atomic plan. Callers must never receive a usable partial plan after a later validation failure.

The exact public API should follow repository style, but the semantic result must expose enough typed truth for later Alpz orchestration to operate without reparsing or re-deriving loader policy.

Conceptually, the successful plan needs facts equivalent to:

LoadPlan
- entry virtual address
- admitted PT_LOAD count
- ordered segment plans
- exact source ELF byte range per segment
- exact destination virtual-memory range per segment
- file byte count
- memory byte count
- zero-fill byte count or range
- read/write/execute permission truth
- alignment information required by the supported contract

Each segment plan should make these relationships explicit:

source_start = p_offset
source_length = p_filesz
memory_start = p_vaddr for the supported first contract
memory_length = p_memsz
zero_fill_length = p_memsz - p_filesz
permissions = truthfully derived from p_flags

Do not store raw unvalidated arithmetic merely because it came from a parsed header.

All additions, ends, conversions, range construction, counts, and capacity boundaries must be checked.

FAILURE ATOMICITY

A later bad PT_LOAD must invalidate the entire plan.

Required behavioral shape:

parse header
→ parse program-header table
→ inspect/validate all relevant load rows
→ validate entry relation
→ only then return a usable complete plan

If segment N is valid and segment N+1 is invalid, the caller must receive an error, not a one-segment usable plan.

Use fixed bounded storage and repository conventions. No hidden heap allocation merely for planning if existing fixed-capacity foundations can express the supported bound cleanly.

ORDERING

Define deterministic output ordering.

Prefer a simple canonical rule such as program-header order if that preserves the loader contract, or ascending virtual address if the reusable module requires canonicalization. Choose one rule, document it, and test it.

Do not accidentally make output depend on hash-map iteration or allocator behavior.

PERMISSION POLICY

The planner must preserve ELF permission truth rather than widen it for convenience.

For the first Batch 22A/22B policy:

- RX is acceptable for executable program bytes;
- RW/NX is acceptable for writable data if such a segment is admitted;
- read-only NX is acceptable if needed;
- W+X must be rejected for the first supported policy;
- executable entry must resolve into an admitted executable segment.

Keep generic ELF flag parsing distinct from policy rejection. If the canonical parser already models flags precisely, reuse that truth.

ZERO-FILL / BSS TRUTH

Even if Batch 22B chooses a tiny fixture where p_filesz == p_memsz, the plan should not lie about p_memsz.

If the reusable abstraction can cheaply and correctly represent p_memsz > p_filesz, represent the zero-fill tail as explicit plan truth and unit-test it.

If supporting that case requires disproportionate new semantics, reject it explicitly for 22A and document the deferral. Do not half-support BSS.

Prefer representation over machine execution: Batch 22A does not need to actually zero physical memory.

OVERLAP POLICY

Do not defer overlap ambiguity into machine integration.

For the first policy, a simple deterministic rejection of overlapping admitted PT_LOAD memory ranges is acceptable and preferred unless the existing canonical contracts already provide a clearly correct stronger policy.

Test boundary-touching half-open ranges separately from actual overlap.

ENTRY POLICY

The plan's entry value must come from the parsed ELF header.

Success requires the entry to lie within an admitted executable PT_LOAD memory range.

Reject at least:

- entry outside every admitted load segment;
- entry in a writable/non-executable data segment;
- entry exactly at the exclusive end of an executable segment;
- overflowed/malformed ranges that make containment unknowable.

REAL RV64 FIXTURE WITHOUT MACHINE EXECUTION

REQUIRED UNIT / NEGATIVE TEST MATRIX

The new or composed planner must test successful and rejecting cases. At minimum cover the behaviors relevant to its supported subset:

SUCCESS

- one valid executable PT_LOAD with entry inside;
- exact source range derived from p_offset/p_filesz;
- exact memory range derived from p_vaddr/p_memsz;
- permission truth preserved;
- deterministic output ordering;
- p_filesz == p_memsz;
- p_memsz > p_filesz representation if supported;
- boundary-touching non-overlapping segments if multiple segments are supported.

REJECTION

- bad ELF magic through canonical parser behavior;
- wrong class;
- wrong endianness;
- wrong machine;
- unsupported ELF type;
- malformed/truncated program-header table;
- zero PT_LOAD if policy requires at least one;
- p_offset + p_filesz overflow/out of input bounds;
- p_filesz > p_memsz;
- p_vaddr + p_memsz overflow;
- unsupported alignment relationship;
- W+X PT_LOAD;
- overlapping admitted PT_LOAD virtual ranges;
- entry outside executable load range;
- entry in non-executable load range;
- entry at exclusive segment end;
- capacity exceeded;
- valid first segment followed by invalid later segment returns no usable partial plan.

Do not duplicate negative tests already exhaustively proven inside the individual canonical parsers unless the composition needs to prove correct error propagation or policy behavior.
