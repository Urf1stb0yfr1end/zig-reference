CORNERSTONE CONSTRAINT
======================================================================

Morphic must remain a cornerstone project: a general foundation upon which future systems can be built without first undoing Linux-specific historical policy.

Therefore every newly required behavior must be classified.

If the pressure exposes a GENERAL MECHANISM, implement the smallest clean Morphic primitive or extend an existing neutral primitive.

If the pressure exposes a LINUX-SPECIFIC REPRESENTATION OR QUIRK, keep it in the Linux compatibility adapter/personality.

Examples:

    permanent mechanism:
        wait/wake
        address-space growth
        file-object metadata query
        file-backed mapping
        task/execution-context creation
        timer source

    compatibility policy:
        Linux syscall number
        negative errno encoding
        mmap flag bit layout
        stat struct layout
        AT_* constants
        ioctl number

Do not define a permanent Morphic object as a Linux fd merely because musl uses fds.

Do not define permanent memory semantics in terms of Linux mmap flags.

Do not define future VM/vCPU semantics in terms of KVM ioctl numbers.

Compatibility may be historically ugly at the edge. The cornerstone should remain neutral at the center.

2. FIRST PRESSURE TARGET: REAL MUSL USERSPACE
======================================================================

Begin with the smallest real external executable that exercises genuine musl startup semantics rather than a project-written assembly fixture.

    real musl static/minimal program

    real musl dynamic hello

======================================================================
4. DYNAMIC LOADER BOUNDARY WIN
======================================================================

One major objective is to transfer dynamic-linking responsibility to the REAL musl loader.

The desired relation is:

    kernel/Morphic:
        load main executable enough to honor PT_INTERP
        resolve/map interpreter through normal file mechanisms
        construct correct process-start state
        provide filesystem/memory/syscall mechanisms
        enter real musl interpreter

    real musl loader:
        parse dynamic metadata
        locate/load required objects
        perform relocations
        resolve symbols
        establish userspace runtime state
        transfer to program entry

Do not parse DT_NEEDED in the kernel merely to make the test pass if musl is supposed to own that work.

Do not perform ELF relocations in the kernel.

A successful real-musl loader transition is a Responsibility Transfer and should be recorded as such.

======================================================================
5. FILE-BACKED MEMORY, IF REAL PRESSURE REQUIRES IT
======================================================================

Batch 26 proved live anonymous mmap. A real loader may require file-backed mappings.

If that becomes the first missing mechanism, implement it as a neutral composition rather than as a musl special case.

A likely clean model is conceptually:

    file/resource object
        + offset/range
        + mapping permissions
        -> address-space mapping backed by object bytes/pages

with Linux mmap flags translated in the compatibility adapter.

Requirements if implemented:

- offset alignment/bounds are explicit;
- mapping identity derives from the actual fd-bound ResourceRef;
- invalid fd/range/protection fails before partial mapping becomes visible;
- W+X policy remains explicit;
- user-visible contents come from the real mapped file bytes;
- independent proof relates file artifact bytes to mapped user memory;
- Linux MAP_* bits remain compatibility policy rather than Morphic ontology.

Do not build demand paging or a page cache unless actual pressure requires them.

An eager bounded file-backed mapping is acceptable if it is the smallest correct reusable mechanism for the current frontier.
