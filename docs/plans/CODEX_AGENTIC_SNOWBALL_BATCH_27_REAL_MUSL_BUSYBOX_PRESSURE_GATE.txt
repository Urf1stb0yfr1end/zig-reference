BATCH 27 STRATEGIC REFINEMENT
======================================================================

The campaign uses a deliberate compromise between two bad extremes:

TOO CEREMONIAL:

    hello
        -> another hello
        -> libc micro-test ladder
        -> many low-leverage milestones
        -> BusyBox someday

TOO BROAD:

    throw a complete dynamic Alpine userspace at an unfinished kernel
        -> many simultaneous failure sources
        -> poor fault localization
        -> long debugging loops

Instead use:

    DIAGNOSTIC MINIMUM
        -> NARROW MULTIPLIER TARGET
        -> DIAGNOSTIC MINIMUM FOR NEXT LAYER
        -> NEXT MULTIPLIER TARGET

A tiny musl program is allowed because it cheaply answers a decisive uncertainty.
It is not itself the inheritance goal.

BusyBox is the first major multiplier target.

The campaign should therefore proceed approximately:

    1. real static musl diagnostic program
        -> prove ordinary real musl C startup can execute
        -> do NOT stop

    2. real static musl-linked BusyBox
        -> busybox true
        -> busybox echo batch27
        -> busybox sh -c 'echo batch27'
        -> first major Boundary Win
        -> do NOT stop

    3. real dynamic musl diagnostic program
        -> isolate the real PT_INTERP / musl-loader / shared-lib boundary
        -> do NOT stop

    4. real dynamically linked BusyBox under real musl
        -> BusyBox applet
        -> BusyBox shell command
        -> second major Boundary Win
        -> do NOT stop

    5. real Alpine RISC-V64 minirootfs / distribution artifact
        -> /bin/sh deterministic command
        -> do NOT stop if apk can be attempted

    6. real apk
        -> apk invocation
        -> preferably apk update or the smallest safe package transaction available
        -> major Inheritance Escape Velocity candidate

If one mechanism collapses multiple levels, take the larger win immediately.
Do not manufacture intermediate batches merely to preserve a roadmap.

======================================================================

    Can the real musl PT_INTERP / dynamic-loader / shared-object startup path execute correctly enough to transfer control to the real program?

    kernel/Morphic:
        honor PT_INTERP

        parse dynamic metadata
        locate/load required objects
        perform relocations
        resolve symbols
        establish userspace runtime state
        transfer to program entry

Do not parse DT_NEEDED in the kernel merely to make the test pass if musl owns that work.
