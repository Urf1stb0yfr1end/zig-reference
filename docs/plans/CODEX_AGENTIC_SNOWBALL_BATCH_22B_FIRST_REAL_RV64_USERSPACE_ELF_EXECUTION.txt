REAL GUEST ELF ARTIFACT

The guest must be an actual separately built ELF artifact, distinct from the Alpz kernel ELF.

It must NOT be:

- a hand-authored instruction byte array inside freestanding_riscv64.zig;
- the existing hardcoded user probe wrapped in decorative metadata;
- a copied slice of the kernel .text presented as a guest;
- a runtime constant claiming to be an ELF without an independently inspectable file artifact.

Prefer a tiny deterministic freestanding RV64 source/build target under an appropriate repository test/fixture location.

The artifact should be produced by the repository build or verifier workflow rather than committed as an opaque binary unless current repository policy explicitly prefers otherwise.

Preferred first fixture:

- ELF64 little endian;
- ET_EXEC;
- RISC-V machine 243;
- no PT_INTERP;
- no dynamic relocation requirement;
- one executable non-writable PT_LOAD;
- p_filesz == p_memsz;
- virtual address arranged to fit the already-proven user code page if practical;
- e_entry inside that PT_LOAD;
- tiny deterministic RV64 instructions;
- one unmistakable register marker or similarly bounded runtime fact;
- one ECALL;
- fail-stop behavior if control unexpectedly continues.

If the existing user geometry remains current, strongly prefer arranging the fixture's executable segment around the already-proven code VA near 0x80401000 and retaining the existing stack near 0x80402000–0x80403000. Confirm actual HEAD before relying on these addresses.

The guest source and guest ELF must have an independently identifiable path in the completion report.

PHYSICAL DESTINATION AND MAPPING POLICY

Reuse the existing proven user code frame and stack if possible.

Preferred smallest path:

existing allocator-owned code physical frame
→ exact PT_LOAD bytes copied into that physical frame through an already-trusted supervisor/physical access path
→ existing U RX PTE remains U RX
→ no transient U W+X mapping
→ no new user mapping
→ no new page-table frame
→ no SFENCE.VMA if no translation changed
→ FENCE.I after executable bytes change

Do not make the U executable page writable merely to simplify loading.

Do not silently widen ELF permissions.

If direct preparation of the physical frame under existing supervisor mappings is already how the historical U-mode probe was installed, reuse and tighten that mechanism rather than inventing a new loader mapping mode.

If actual HEAD proves a mapping change is unavoidable, use the canonical page-table builder/invalidation foundations, preserve W^X, prove the exact transition mechanically, and explain why reuse was insufficient. This is a fallback, not the preferred path.

BYTE-COPY TRUTH

Copy exactly the planner-described source bytes for the admitted executable segment.

For the preferred p_filesz == p_memsz fixture:

- copied byte count must equal plan.file_byte_count;
- zero_fill_byte_count must equal zero;
- do not invent BSS work.

If the final fixture unexpectedly has a nonzero zero-fill tail, either:

1. implement exact zeroing through a bounded trusted physical path and prove it; or
2. simplify the fixture back to p_filesz == p_memsz.

Prefer option 2 for Batch 22B.

The proof must tie the bytes at the execution destination to the exact ELF PT_LOAD source range before U-mode entry.

A bounded checksum/digest or exact-byte comparison is acceptable as supporting evidence if independently reconstructed by the verifier.

Do not prove only that "some bytes were copied."

INSTRUCTION-CACHE SYNCHRONIZATION

Because executable memory contents change, execute the required RISC-V instruction-cache synchronization before entering the newly loaded code.

Prefer the smallest architecturally correct FENCE.I path.

Evidence must distinguish instruction-cache synchronization from address-translation invalidation.

If PTEs are unchanged, report that SFENCE.VMA was not required rather than emitting one ceremonially.

ENTRY TRUTH

The U-mode entry PC must come from LoadPlan.entry.

The actual SRET preparation path must consume that value.

The external verifier must independently inspect the real guest ELF and reconstruct e_entry.

It must then require agreement among at least:

- guest ELF e_entry;
- Batch 22A planner evidence;
- supervisor prepared user entry;
- observed U-mode execution/trap evidence.

A hardcoded address plus equality printout is not sufficient proof.

GUEST EXECUTION PROBE

Keep the guest tiny.

At its real ELF entry it should perform a deterministic sequence that is distinguishable from the historical hand-copied probe.

Recommended shape:

_start:
    establish one or more unmistakable register marker values
    optionally perform a bounded stack touch using the existing proven U RW/NX stack
    ecall
    fail-stop if execution unexpectedly resumes

Do not use Linux syscall conventions. The ECALL is a proof signal, not a Linux syscall.

The marker should be chosen so the supervisor/verifier can distinguish the new ELF guest from Batch 19/20/21 historical probes.

TRAP / RETURN PROOF

The existing trusted U→S path is already proven and should be reused.

Batch 22B must prove the trap was caused by the ELF-loaded U-mode program, including at minimum:

- expected U-mode ECALL cause;
- expected user PC relationship to the real guest e_entry/code;
- expected marker register state from the ELF guest;
- trusted supervisor trap-frame/stack path remains in use;
- supervisor control reaches a known bounded continuation after the trap.

Do not redesign the trap frame unless a concrete defect requires it.

RESOURCE AND PTE CONSERVATION

The preferred Batch 22B result should preserve the existing Batch 21C resource geometry.

Where applicable, require mechanical evidence that:

- allocator-owned frame count is unchanged across ELF execution preparation;
- page-table frame count is unchanged;
- active SATP/root identity is preserved;
- existing user code page maps the expected physical frame;
- existing user stack maps the expected physical frame;
- executable page remains U RX and not writable;
- stack remains U RW/NX;
- W+X leaf count remains zero;
- no unexpected additional U leaf appears.

If the implementation legitimately changes one of these facts, the verifier must reconstruct and justify the new truth. Do not silently relax conservation assertions.
