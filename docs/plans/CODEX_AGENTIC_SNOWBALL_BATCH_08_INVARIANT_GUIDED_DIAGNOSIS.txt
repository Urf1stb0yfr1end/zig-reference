CODEX AGENTIC SNOWBALL BATCH 08 — INVARIANT-GUIDED DIAGNOSIS

MISSION

Build the smallest reusable architecture that lets an agent continue from a concrete failure state to an evidence-backed diagnosis, repair path, and focused validation without reopening the whole subsystem.

This is the first architecture batch after Batch 07 Correct-Use Preflight and its independent repair.

Batch 07 established the forward correct-use path:

goal
→ decide
→ card/select
→ compose
→ preflight
→ integrate
→ validate

Batch 08 establishes the beginning of the reverse failure path:

failure
→ Failure State Capsule
→ Invariant-Guided Diagnosis
→ stable diagnosis OR explicit UNKNOWN
→ repair
→ focused validation

The governing idea is symmetry:

PRE-FLIGHT:
"These are the invariants and obligations you must preserve."

POST-FAILURE:
"These are the observed facts. Which canonical invariant, if any, do they establish was violated?"

ARCHITECTURAL REQUIREMENT 1 — CANONICAL INVARIANTS

A diagnosis must point to canonical engineering truth, not to a second manually maintained explanation of the same rule.

Determine the smallest durable way to represent correctness-relevant invariants in the canonical contract architecture.

Requirements:

- invariants must have stable machine-readable identity;
- invariants must be attached to the component/operation/state where they actually apply;
- wording should use normal programming language;
- the source of truth must be canonical and mechanically validated;
- generated agent projections may derive from canonical invariants but must not become a second authored database;
- diagnostics may reference invariants but must not copy their truth into an independently drifting prose field;
- invariants should be optional where a module genuinely has no currently authored invariant evidence;
- do not manufacture superficial invariants merely to increase coverage;
- do not require all 53 modules to be rewritten in this batch.

If the existing contract schema already contains an equivalent fact under another normal field, reuse/strengthen it rather than creating a duplicate representation.

Prefer a small number of strong invariants over an exhaustive list of restated implementation details.

Examples of the KIND of invariant intended, not mandated exact text:

- logical time does not move backward;
- a bounded container cannot accept an element beyond capacity;
- a sealed resource plan cannot acquire resources outside the established plan;
- an address/mapping operation requires alignment or non-overlap when that is actually true in the canonical implementation.

Do not add an invariant unless source, contract, and executable evidence support it.

ARCHITECTURAL REQUIREMENT 2 — FAILURE STATE CAPSULE

Create the smallest conventional machine-readable representation necessary to carry decisive failure state into diagnosis.

Use JSON and the repository's existing schema placement/versioning conventions.

Do not invent a bespoke textual DSL.
Do not require agents to parse human logs when structured facts are available.
Do not stuff raw stack traces or arbitrary complete program state into the capsule.
Do not make the capsule a duplicate of the full module contract.

A capsule should contain only facts that are useful for diagnosis continuation.

Based on actual pressure evidence, likely useful categories include:

- schema/version identity if the repository convention requires one;
- component;
- operation;
- native error or symptom when available;
- relevant observed values/state;
- relevant boundary/expected value only when factual and available;
- mutation/rollback status only when actually established;
- minimum useful locations when known;
- explicit unknown/unavailable facts where needed.

Those are requirements-by-purpose, not a mandated exact schema.

Design the schema from real pressure cases.

The capsule must be:

- deterministic;
- compact;
- schema-valid;
- evidence-honest;
- easy for a generic coding agent to understand from standard terminology;
- sufficient to distinguish at least the known pressure diagnoses from deliberately ambiguous/insufficient cases.

If a field is unnecessary to establish any pressure diagnosis, question whether it belongs in the first version.

ARCHITECTURAL REQUIREMENT 3 — INVARIANT-GUIDED DIAGNOSIS

Add a deterministic structured diagnosis path that consumes a valid Failure State Capsule and attempts to identify a violated canonical invariant.

The normal path should not parse implementation source.

The normal path should use canonical/generated repository truth already intended for machine consumption.

The result must clearly distinguish at least:

KNOWN
- evidence establishes a specific canonical invariant violation;
- identify component and operation;
- identify invariant by stable identity;
- surface the matching stable diagnostic when one exists/was justified;
- give the repair strategy/evidence path;
- give focused validation;
- give the minimum useful locations.

UNKNOWN / INSUFFICIENT EVIDENCE
- evidence does not establish a unique invariant;
- do not rank a guess as causal truth;
- return the existing explicit unknown diagnostic semantics (`ZIGREF-DIAGNOSIS-UNKNOWN`) or the repository's actual canonical equivalent;
- explain which decisive evidence is absent or ambiguous when this can be stated mechanically;
- provide the smallest next inspection/query step.

INVALID CAPSULE
- malformed/unsupported structured input;
- nonzero exit;
- stable repository error identity if existing conventions justify one;
- repair should point to schema/usage rather than guessing about the underlying program failure.

A native error name alone is not automatically enough to claim invariant causality unless the canonical contract proves that the error uniquely establishes that invariant.

A caller-provided assertion like `violated_invariant = X` must not be blindly trusted as diagnosis evidence. The system's purpose is to derive or verify the diagnosis from canonical truth + observed state, not simply echo the caller's conclusion.
