CODEX AGENTIC SNOWBALL BATCH 07 — CORRECT-USE PREFLIGHT

MISSION

Strengthen zig-reference so a coding agent can discover the correctness obligations of a module or composition before it writes substantial integration code.

This batch exists to answer a serious competitive question:

Why should an autonomous coding agent choose zig-reference over beginning from Rust, C, raw Zig, or a pile of unrelated libraries?

Do not answer with rhetoric.

Make the repository cheaper to use correctly.

Rust has a powerful compiler that rejects many ownership, borrowing, lifetime, and type mistakes in newly written code. zig-reference must not pretend to replace rustc, clone a borrow checker, or reproduce every compiler diagnostic.

Instead, zig-reference should make the comparison structurally different:

- reuse validated canonical code instead of rewriting solved mechanisms;
- expose ownership, borrowing, invalidation, state, resource, environment, and failure constraints before integration;
- make invalid states harder to represent in Zig APIs where practical;
- mechanically validate repository-specific invariants the language cannot know;
- surface known misuse and repair knowledge cheaply;
- tell the agent exactly what remains uncertain;
- preserve native compiler errors and exact source truth;
- keep the ordinary decision surface compact enough that using the repository costs less context than rediscovering it.

The governing idea is simple:

The safest newly written systems code is the code the agent discovers it did not need to write.

And for the code that genuinely must be written:

Expose the important correctness obligations before the first edit.

This batch should make that practical and measurable without inventing a private programming language, a new type system, or a giant static-analysis project.

OBJECTIVE 1 — DEFINE THE CORRECTNESS BOUNDARY CLEARLY

Do not compete with language compilers by duplicating what they already know.

Native Zig compiler output remains authoritative for Zig syntax, typing, comptime behavior, and compilation.

zig-reference should add only higher-level engineering truth that changes an agent's next decision, such as:

- who owns storage;
- what is borrowed;
- how long a borrow remains valid;
- what operations invalidate a view or handle;
- what state transitions are legal;
- what resources are bounded;
- what may allocate;
- what must be initialized first;
- what a failed mutation preserves;
- what ordering is deterministic;
- what environment assumptions apply;
- what known misuse means;
- what exact repair and focused validation are known.

Do not author thousands of possible error descriptions.

Prefer a small number of high-value correctness obligations and evidenced diagnostics over exhaustive prose.

The repository should preserve native failures and add repository-specific context only where the repository genuinely knows more than the compiler.

OBJECTIVE 2 — ADD A COMPACT PRE-INTEGRATION CORRECTNESS VIEW

Inspect the existing Agent Fast Path and query-reference architecture before changing it.

Add the smallest coherent machine-facing operation that lets a zero-context coding agent ask:

"What must I preserve to use this module or composition correctly?"

Prefer extending the existing query-reference interface rather than creating a second tool.

A command shaped approximately like this is acceptable if it fits the existing CLI cleanly:

python3 tools/query-reference.py agent preflight MODULE_OR_RECIPE

The exact syntax may differ if the current parser or conventions make another form more coherent. Do not create a private DSL.

The preflight response must be deterministic JSON and derived from existing canonical contracts/indexes wherever possible.

Do not create a parallel authored metadata system just for this view.

For a module or composition, return only correctness-critical obligations that the agent should know before integration.

Where applicable, include compact fields covering:

- subject identity;
- subject kind: module or recipe/composition;
- Zig baseline;
- environment constraints;
- dependency/build order or closure reference;
- ownership obligations;
- cleanup obligations;
- borrowing obligations;
- invalidation rules;
- resource/capacity/allocation constraints;
- state-transition constraints;
- failure/error obligations;
- failure atomicity when known;
- deterministic ordering/time assumptions when relevant;
- known diagnostics relevant to misuse;
- focused validation or validation closure;
- minimum useful locations;
- unresolved or unrepresented correctness facts, if any.

Do not include empty prose sections merely for symmetry.
Do not copy long documentation passages.
Do not dump all tests, all symbols, all diagnostics, or all source paths.

The default output should be the cheapest sufficient correctness surface.

If a full contract has all information needed, ordinary preflight must not require implementation-source inspection.

OBJECTIVE 3 — NO FALSE SAFETY

The preflight view must never become more permissive than canonical truth.

This is Constraint-Preserving Compression.

If a correctness-critical fact is absent from the compact projection but present in canonical metadata, repair the projection.

If the repository does not know a fact, return an explicit unknown/unrepresented state instead of guessing.

Examples:

- unknown lifetime must not become "stable";
- unknown allocation behavior must not become "allocation-free";
- missing failure-atomicity evidence must not become "atomic";
- a documented misuse example must not become a compile-time guarantee;
- runtime-negative evidence must not become proof of impossibility;
- a compiler-checked property may be described as compiler-checked only when that claim is actually demonstrated by the source/build path.

Add negative tests that reject or expose projection loss for correctness-critical fields.

OBJECTIVE 4 — MAKE INVALID USE HARDER WHERE ZIG CAN EXPRESS IT CLEANLY

Use the Batch 06 Morphic composition and a small high-leverage sample of existing modules as a pressure test.

Do not redesign every module in the repository.

Select the smallest set of modules/composition boundaries whose semantics meaningfully exercise:

- ownership;
- borrowed views;
- invalidation;
- bounded resource use;
- stable identity/handles;
- state transitions;
- deterministic ordering;
- allocation after initialization;
- explicit cleanup.

The sample should include the new/changed Batch 06 Morphic foundations and may include existing modules such as owned-byte-buffer, intrusive-doubly-linked-list, optional-typed-handle, fixed-capacity-object-pool, state-machine, or other better-fitting current modules.

For each selected boundary, inspect whether a correctness rule currently exists only as prose but can be moved into ordinary Zig structure without making the API worse.

Prefer, where appropriate:

- precise types instead of raw integers;
- opaque or typed handles instead of ambiguous indices;
- explicit error unions instead of sentinel states;
- caller-owned storage when that is the contract;
- compile-time capacity where that is truly part of the type;
- explicit initialization/deinitialization;
- state-machine APIs that reject invalid transitions;
- checked conversions;
- explicit invalidation/reacquisition behavior;
- narrow public APIs rather than mutable internal state exposure.

Do not contort normal Zig merely to imitate Rust.
Do not add lifetimes as a private annotation language.
Do not add procedural macros, code-generation frameworks, or a second compiler.

Only change an existing public API when the correctness improvement materially justifies it and affected dependents can be migrated safely in the same run.

OBJECTIVE 5 — BUILD MISUSE FIXTURES THAT TEACH THE AGENT WHAT THE COMPILER CANNOT

For the selected high-leverage boundaries, create focused misuse/negative fixtures when current evidence is insufficient.

Test actual repository contracts, not hypothetical bug lists.

Examples where applicable:

- stale handle after generation change;
- use of a borrowed view after an invalidating mutation;
- double insertion of an intrusive node;
- invalid state transition;
- resource exhaustion at exact capacity;
- forbidden post-initialization allocation;
- deterministic tie ordering;
- cleanup/ownership misuse that can be detected safely;
- output/trace capacity exhaustion;
- failure atomicity after a rejected mutation.

Distinguish evidence classes honestly.

If Zig can reject a misuse at compile time, preserve compiler output in the evidence path.
If the misuse can only be detected at runtime, say so.
If the rule is documented but cannot currently be mechanically enforced, say so.

Do not convert a runtime test into a stronger type-system claim.

OBJECTIVE 6 — CONNECT KNOWN MISUSE TO THE DEBUG FAST PATH

Use existing ZIGREF diagnostics where they already represent the exact stable meaning.

If the pressure test reveals a recurring, generally useful misuse with a stable meaning and repair path, add a new ZIGREF diagnostic only when evidence supports it.

A useful diagnostic should let a cold agent reach, cheaply:

native symptom/error
→ stable diagnostic identity
→ violated repository rule
→ likely operation/component
→ repair strategy
→ minimum useful locations
→ focused validation

Do not duplicate native compiler diagnostics just to increase diagnostic count.
Do not create one ZIGREF ID for every compiler message.
Do not hide native errors.
Do not invent a cause for an unknown symptom.

Optimize for Diagnostic Reach and Repair Locality, not raw diagnostic volume.

OBJECTIVE 7 — VALIDATION CLOSURE MUST BE CHEAP

The preflight result should expose the smallest meaningful validation path for the selected module/composition.

Do not make a coding agent run the entire repository after every edit when focused validation exists.

Where current generated metadata can derive Validation Closure, use it.

Where it cannot, improve the existing derivation architecture rather than hand-maintaining a second command list.

For a typical module integration, the agent should be able to identify:

- focused unit command;
- focused smoke command;
- directly relevant recipe/composition validation when applicable;
- stronger aggregate gate required before completion.

The repository should minimize Validation Distance while preserving final repository-wide validation.
