CODEX AGENTIC SNOWBALL BATCH 07 — CORRECT-USE PREFLIGHT

MISSION

Strengthen zig-reference so a coding agent can discover the correctness obligations of a module or composition before it writes substantial integration code, while first repairing two machine-facing truth failures discovered by independent review of Batch 06.

This batch exists to answer a serious competitive question:

Why should an autonomous coding agent choose zig-reference over beginning from Rust, C, raw Zig, or a pile of unrelated libraries?

Do not answer with rhetoric.

Make the repository cheaper to use correctly.

LONG-TERM COMPETITIVE AIM

The long-term research ambition is stronger than merely making Zig pleasant to use.

Within domains that zig-reference genuinely covers, drive total agent Cost of Correct Use, diagnosis, repair, validation, and required new implementation low enough that a capable coding agent may rationally prefer the zig-reference path even when a strong Rust/rustc-centered workflow is available.

This is not a present claim that zig-reference equals or exceeds the Rust compiler, borrow checker, Rust memory-safety model, or Rust ecosystem. It is a falsifiable engineering target that must eventually be tested on comparable tasks.

Do not game that future comparison by hiding failures, weakening correctness, or moving work outside the measured path. The intended win is practical: preserve more solved engineering knowledge, expose more decisive state, require less rediscovery and reimplementation, and reach a correct validated result with less total agent work in the covered problem domain.

Rust has a powerful compiler that rejects many ownership, borrowing, lifetime, and type mistakes in newly written code. zig-reference must not pretend to replace rustc, clone a borrow checker, or reproduce every compiler diagnostic.

Instead, zig-reference should make the comparison structurally different:

- reuse validated canonical code instead of rewriting solved mechanisms;
- expose ownership, borrowing, invalidation, state, resource, environment, and failure constraints before integration;
- make invalid states harder to represent in ordinary Zig APIs where practical;
- mechanically validate repository-specific invariants the language cannot know;
- mechanically detect contradictions between canonical source truth and machine-facing projections;
- surface known misuse and repair knowledge cheaply;
- tell the agent exactly what remains uncertain;
- preserve native compiler errors and exact source truth;
- keep the ordinary decision surface compact enough that using the repository costs less context than rediscovering it.

The governing ideas are simple:

The safest newly written systems code is the code the agent discovers it did not need to write.

And for the code that genuinely must be written:

Expose the important correctness obligations before the first edit.

But compactness is useful only when the compact surface is truthful.

A structurally valid machine-readable contract that names the wrong public API is worse than no compact contract at all because it gives the agent cheap confidence in false information.

Therefore Batch 07 begins by repairing the two Batch 06 independent-review failures and teaching the repository to reject those failure classes in the future.

This batch should make correct reuse practical and measurable without inventing a private programming language, a new type system, or a giant static-analysis project.

OBJECTIVE 4 — NO FALSE SAFETY AND NO FALSE CANONICALITY

The preflight view must never become more permissive, more confident, or more canonical than repository truth supports.

This is Constraint-Preserving Compression.

If a correctness-critical fact is absent from the compact projection but present in canonical metadata, repair the projection.

If the repository does not know a fact, return an explicit unknown/unrepresented state instead of guessing.

If two claimed truth surfaces contradict each other, do not silently choose one. Repair the contradiction when authoritative source truth establishes the answer; otherwise expose the unresolved inconsistency.

Examples:

- unknown lifetime must not become stable;
- unknown allocation behavior must not become allocation-free;
- missing failure-atomicity evidence must not become atomic;
- a documented misuse example must not become a compile-time guarantee;
- runtime-negative evidence must not become proof of impossibility;
- a compiler-checked property may be described as compiler-checked only when that claim is demonstrated by the actual source/build path;
- an imported dependency symbol must not become the module's claimed public symbol merely because a static scanner encountered it;
- a runnable serious verification command must not be documented as canonically wrapped if the Developer Minimus outer operation does not exist.

Add negative tests that reject or expose Projection Loss and correctness-critical cross-surface contradictions.
