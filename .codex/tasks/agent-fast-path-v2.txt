Work in the existing repository at ~/dev/zig-reference.

Use Zig 0.14.0.

Read AGENTS.md first.

This task is not about adding another Zig systems module.

This task is about making zig-reference extraordinarily easy for any coding agent to use, including an agent that has never seen this repository before, has no prior conversation context, does not know our conventions, and is trying to minimize context, searches, retries, source reads, and wasted compute.

The repository should become self-explanatory.

A zero-context agent should be able to arrive, run one obvious bootstrap query, discover what the repository can do, select or reject modules, compose existing capabilities, obtain a tiny integration card, determine what remains genuinely missing, implement only that missing work, validate it, and repair recognized failures without recursively reading the repository.

The intended future workflow is:

task
→ bootstrap
→ decide
→ select or reject
→ compose
→ integrate
→ implement only missing work
→ validate
→ repair through stable diagnostics

The desired end state is not “more documentation.”

The desired end state is precomputed engineering memory.

The repository should tell the agent what is already known so the agent can spend its reasoning budget on what is actually new.

Do not create a branch, commit, push, tag, open a pull request, or otherwise modify GitHub. Work only in the local repository and leave completed changes uncommitted for review.

TOOL FAILURE STANDARD

Agent-facing tooling must never silently fail.

Use normal Unix conventions.

Machine-readable command output belongs on stdout.
Progress, debug/status information, and human-readable failure information belong on stderr so they never corrupt structured stdout.

On failure:

return a nonzero exit status
identify the failed operation
identify the affected path/module/recipe when known
print a stable ZIGREF-* diagnostic when the failure has a known repository meaning
print the exact reason
print the next focused inspection or repair command when known

Do not:

silently skip malformed entries
silently substitute a fallback
silently retry forever
silently ignore stale indexes
silently ignore missing files
silently swallow subprocess exit codes
convert partial failure into success
claim generated state is current when it is not

If a fallback is deliberately supported, report that the fallback occurred and why.

ANTI-STALL AND MINIMAL DEBUG LOGIC

Add minimal debug/status logic to the repository tooling where it materially helps agents understand progress.

Do not build a logging framework.
Do not spam one message per item during large scans.

Useful information includes:

phase name

A good long operation should look conceptually like:

or, on failure:

Do not require an agent to wonder whether a command is hung.

Where subprocesses or retries exist, keep them bounded.
Do not introduce arbitrary retries merely because retry support is requested.
If a subprocess timeout is appropriate and can be added without destabilizing existing behavior, use a reasonable explicit timeout and report timeout failure clearly.
Inspect existing shared Python helpers before duplicating status/debug code across tools.

determinism

Short, literal statements of capabilities callers commonly expect but this module deliberately does not provide.

One extremely small canonical integration sequence.
Not a tutorial.
Not copied README prose.
Just enough to show normal construction and use.

integration_notes

A short list containing only genuinely non-obvious integration facts not already expressed structurally.
If there are no useful notes, allow an empty list.
Do not fill fields with fluff.

Consider whether one or two additional fields are genuinely required after inspecting the repository.
Do not exceed the smallest useful schema.
